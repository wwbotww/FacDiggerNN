## 1. 如何使用这份文档

面试时不要从目录结构开始背诵项目。更有效的讲法是：

1. 用 30 秒说明项目目标；
2. 选择一个与岗位最相关的关键问题；
3. 按“现象 → 根因 → 方案权衡 → 最终设计 → 验证 → 局限”展开；
4. 最后说明如果数据、算力或时间更充足，下一步怎样升级。

本文给问题标注三种证据等级：

| 标记 | 含义 |
|---|---|
| `实际运行故障` | 在真实命令或真实 EODHD 数据上已经触发 |
| `工程验证暴露` | 在兼容性探针、单元测试、集成测试或跨平台运行中发现 |
| `研究审查发现` | 代码可以运行，但结果可信度检查发现不能直接用于正式结论 |

这一区分很重要。面试时可以坦诚地说：“这个问题不是线上事故，而是我在正式实验前通过门禁主动发现并阻断的。”这通常比夸大故障更能体现工程判断。

## 2. 项目的一句话介绍

FacDiggerNN 是一个面向美股日频横截面选股的机器学习因子研究工具。它以 EODHD 为首个数据源，以 PatchTST 为时序编码器，比较：

- `E0`：LightGBM / MLP 传统基线；
- `E1`：随机初始化 PatchTST；
- `E2`：从 IBM ETTh1 PatchTST 迁移；
- `E3`：ETTh1 迁移后继续做金融域 masked-patch 预训练。

项目重点不是“训练出一个模型”，而是把数据、点时语义、防泄漏训练、权重迁移、统一评价、Walk-forward、holdout 冻结、checkpoint 回放和无标签因子导出连成一条可审计链路。

## 5. 旗舰案例：EODHD 同一 ISIN 导致重复主键

### 5.1 证据与影响

- 证据等级：`实际运行故障`
- 触发命令：

```bash
uv run facdigger data ingest \
  --config configs/data/eodhd_historical_liquid.yaml
```

- 真实错误：

```text
bars_daily has duplicate keys ['security_id', 'trade_date']
```

- 已观察到的冲突包括：

```text
eodhd:isin:KYG330331201
eodhd:isin:US00258Y1047
eodhd:isin:KYG330321061
```

这个错误由标准表契约在写入 Parquet 前阻断。如果没有唯一键门禁，重复记录会进入 rolling feature、标签和横截面排序，后续结果可能仍能生成，但一个证券会在同一天出现两次，属于“静默污染”。

### 5.2 根因不是单一的“脏数据”

真实数据检查发现存在两类完全不同的冲突。

第一类是 EODHD 元数据的证券类型泄漏：

```text
AACT      Ares Acquisition Corporation II
AACT-WT   Ares Acquisition Corporation II WT
```

二者被标为 `Common Stock`，并共享 `KYG330331201`，但价格显然属于普通股和权证两个不同工具，不能按同一证券合并。

第二类是真实 ticker 迁移或别名：

```text
ABX
ABL
```

二者共享 `US00258Y1047`，EOD endpoint 返回大量重叠历史；同一天的 OHLC 基本相同，但 volume 可能有轻微舍入差异。这一类应该保持证券历史连续，而不能被拆成两个独立公司。

### 5.3 为什么几个直觉方案都不够好

方案一：直接把 `security_id` 改成 ticker。

- 优点：立即消除重复键。
- 问题：ticker 会变化；公司改名或换代码后历史被切断。
- 后果：rolling feature、上市天数、退市判断和训练窗口全部出现人为断点。

方案二：遇到重复行就 `unique(keep="first")`。

- 优点：代码最短。
- 问题：结果取决于 API 顺序和 batch 顺序，不具确定性。
- 问题：可能把权证价格当成普通股，也可能丢掉旧 ticker 独有的早期历史。

方案三：所有相同 ISIN 都无条件合并。

- 优点：保持 ticker 迁移连续。
- 问题：EODHD 的权证、单位和 rights 可能与普通股共享 ISIN 或被错误标型。
- 后果：会把价格量级完全不同的证券拼成一条时间序列。

### 5.4 最终采用的两层修复

第一层：候选发现阶段修正明显的证券类型泄漏。

- 保留 provider 的 `Type` 初筛；
- 再检查名称中的 `warrant`、`unit`、`right`；
- 检查 `-WT`、`-UN`、`-RT` 等衍生代码后缀；
- 对无分隔符的 `W/U/R` 后缀，仅在存在同名基础 ticker peer 时排除，降低误杀普通公司的风险；
- 在 manifest selection audit 中记录排除数量。

第二层：对真正的 ticker alias 合并历史。

- 稳定身份仍优先使用 ISIN；
- 非重叠日期全部保留，避免丢失旧 ticker 独有历史；
- 重叠日期优先当前 active alias；
- 其次优先历史覆盖终点更晚的 alias；
- 最后按 provider symbol 排序，保证确定性；
- batch 内和所有 batch concat 后都执行一次，避免同一 ISIN 跨 250-symbol batch 时再次冲突；
- manifest 记录 `overlapping_alias_rows_resolved`。

### 5.5 验证

- 新增 ticker alias 重叠测试；
- 新增衍生工具过滤测试；
- 原 EODHD adapter 测试全部通过；
- 全项目 72 项测试通过；
- 复用已有 977 个 API 缓存响应恢复真实采集，API 调用继续增长，原重复键没有在相同位置再次触发。

### 5.6 面试讲法

> 我在第一次全量下载 2 万多只美股历史时，标准表唯一键门禁拦住了重复的 `(security_id, trade_date)`。继续看真实 payload 后发现这不是普通 dedup：一部分是 ticker rename，应该合并；另一部分是 EODHD 把权证和 unit 错标成 Common Stock，而且它们还共享 ISIN，绝对不能合并。我最后做了两层设计：先用名称、后缀和 peer ticker 修正衍生品泄漏，再对真正的 alias 保留非重叠历史，并用 active、覆盖终点和 ticker 做确定性重叠选择。这个方案没有退化成用 ticker 当主键，也不会因 API 返回顺序改变结果。

### 5.7 尚存局限

- ISIN 本身也可能存在供应商错误；
- 规则型衍生品识别不能替代完整 security master；
- 最终全量 Parquet 和 selection audit 仍需在采集完成后检查；
- 更成熟的方案是接入带 `effective_from/effective_to` 的 ticker mapping 和 instrument type 主数据。

### 5.8 后续真实故障：零价占位和不一致 OHLC

DATA-01 修复后，采集从 977 个缓存响应继续到 1190 个，随后再次被数据契约阻断：

```text
bars_daily has 24 invalid OHLCV/adjustment rows
```

扫描当时已有缓存，共发现 15 个 symbol、33 行非法观测，主要分为：

1. 全部 OHLC、adjusted close 和 volume 都是 0 的 provider 占位记录；
2. `low > close` 或 `high < close` 的内部不一致 OHLC；
3. 前一版过滤规则漏掉的 `AAGRW`、`ACABW`、`ACII-U`、`ACHR-WS` 等衍生工具。

真实样例：

```text
ACAQ.US  2023-11-06  open=0 high=0 low=0 close=0 adjusted_close=0 volume=0
ACII-U.US 2021-02-12 open=10.95 high=11.25 low=10.895 close=10.85
ACHR-WS.US 2024-06-28 open=0.334 high=0.355 low=0.334 close=0.3725
```

这里没有采用以下“修复”：

- 把 0 价格替换为前值：这会凭空制造可交易价格和成交；
- 强行令 `high=max(open, high, close)`：这会掩盖供应商错误；
- 关闭 OHLCV contract：这会让错误进入特征和标签；
- 遇到坏行删除整只股票：这会不必要地损失其他有效历史。

最终处理分两层：

- 扩展衍生工具识别，覆盖显式 `-U/-WS`，以及 Nasdaq 常见的第五字符 `W/U/R` 和 `_OLD` alias；
- provider 映射前检查 finite、正价格、OHLC 包含关系、非负 volume 和正复权因子；
- 只丢弃非法“观测行”，不修造价格；
- 后续 universe 全市场 session 网格仍保留该日期，并将缺失观测显式表示为 halt/missing；
- manifest 记录 `invalid_eod_rows_dropped`、相关 symbols 和 warning。

这次修复新增 provider placeholder 测试，项目测试总数增至 72。

面试时可概括为：

> 数据清洗不是让 contract 不报错，而是决定错误信息应该怎样进入研究语义。对 0 价占位，我没有 forward-fill 或修改 high/low，而是把它当成“不存在可信 bar”。删除坏观测后，市场 session 仍在 universe grid 中保留，因此下游看到的是显式 missing/halt，而不是一根伪造 K 线。

## 6. 从“当前最活跃 100 只”升级为历史动态股票池

### 6.1 证据与问题

- 证据等级：`研究审查发现`
- 早期 paid pilot 从“今天仍 active 的股票”中按当前 200 日平均成交量选 100 只，再回看历史。

工程上它很方便，但研究上有两个偏差：

1. 存活偏差：历史上退市的公司完全不在样本中；
2. 历史前视偏差：用今天的流动性决定多年前的股票池。

这会系统性高估策略表现，尤其会忽略破产、并购和低流动性退出样本。

### 6.2 最终设计

- 候选发现同时读取 active 和 delisted 普通股；
- 候选阶段不使用当前流动性排名；
- 对每只证券恢复上市区间内的全市场 session 网格；
- 仅用截至当日的 trailing ADV20；
- 每个历史交易日独立选取最多 1000 只；
- 记录候选规模、active/delisted 数量、排名规则和 research readiness。

这里的关键拆分是：

```text
候选发现：谁在历史上可能存在
        ↓
点时 eligibility：某只股票在某一天是否可交易、是否足够流动
```

两者不能合并成“先用今天的数据选一批股票，再回测”。

代码证据：

- [`configs/data/eodhd_historical_liquid.yaml`](../configs/data/eodhd_historical_liquid.yaml)
- [`src/facdigger/data/providers/eodhd/universe.py`](../src/facdigger/data/providers/eodhd/universe.py)
- [`src/facdigger/data/providers/eodhd/mapper.py`](../src/facdigger/data/providers/eodhd/mapper.py)

### 6.3 面试讲法

> 最开始的 100 股票 pilot 只用于证明系统能跑通。我没有把它包装成正式回测，因为它先看了今天谁还活着、谁现在最流动，再回到历史。正式协议把 candidate discovery 和 daily eligibility 分开：candidate 纳入 active 和 delisted，daily eligibility 只使用当时能知道的 trailing ADV20。这样工程 pilot 和研究结论的边界是显式的。

## 7. 标签终点不能按“个股第 5 根 K 线”推进

### 7.1 证据与问题

- 证据等级：`研究审查发现`
- 目标是预测全市场交易日 `t+5` 的 next-open 到 next-open 超额收益。

如果按每只股票自身的第 5 个后续观测推进，停牌一天的股票会把标签终点移到市场 `t+6`。不同股票的“5 日收益”实际对应不同持有期，横截面不可比，也产生对停牌状态的选择偏差。

### 7.2 最终设计

- 从所有日线构建全市场 session 日历；
- `label_start` 和 `label_end` 通过市场 session 位移得到；
- 股票某个 session 缺少 bar 时，在 universe grid 中显式标记 `is_halted`；
- 标签不能偷偷寻找更晚的一根个股 K 线替代目标日；
- 若窗口跨退市，则进入退市 terminal value 分支。

代码证据：

- [`src/facdigger/labels/forward_return.py`](../src/facdigger/labels/forward_return.py)
- [`src/facdigger/data/providers/eodhd/mapper.py`](../src/facdigger/data/providers/eodhd/mapper.py)
- [`tests/integration/test_dataset_pipeline.py`](../tests/integration/test_dataset_pipeline.py)

### 7.3 面试讲法

> 一个容易忽略的问题是 horizon 到底是“市场过去 5 个 session”还是“这只股票出现 5 根 K 线”。后者遇到停牌会错位。我把 universe 做成证券 × 市场 session 网格，标签终点由全市场日历定义，缺失 bar 明确标成停牌或缺失，不允许向后偷找价格。

## 8. 没有真实退市收益时，如何避免静默删除失败样本

### 8.1 证据与问题

- 证据等级：`研究审查发现`
- 当前 EODHD 套餐能提供 delisted 列表，但没有足够可靠的退市原因和 terminal return。

如果一只股票在标签窗口内退市，`label_end` 没有正常价格。最简单的实现会得到 null 并删除样本，而这些样本通常表现更差，删除它们会形成系统性乐观偏差。

### 8.2 最终设计

工程阶段采用明确、版本化的交易所惩罚假设：

| 交易所 | 默认 `delisting_return` |
|---|---:|
| Nasdaq | -55% |
| NYSE / NYSE American | -30% |
| 未知 | -50% |

具体约束：

- 插值表逐行标记 `is_imputed=true`；
- 记录 `imputation_method` 和 exchange；
- source manifest 写入完整政策和警告；
- 标签窗口跨退市时，用最后有效价格乘 `(1 + delisting_return)`；
- 数据仍标记为不满足正式 research readiness；
- 实验文档要求对惩罚参数做敏感性分析。

这不是声称插值“正确”，而是把未知问题从静默删除变成显式、可复核的假设。

代码证据：

## 9. 数据源适配：避免把 EODHD 字段写进整个项目

### 9.1 证据与问题

- 证据等级：`工程验证暴露`
- EODHD 使用 `adjusted_close`、`Isin`、`Code`、`Exchange` 等供应商字段；后续更换供应商时字段和语义都会变化。

如果 feature、label 和 model 直接读取这些字段，数据源会成为全项目的结构性依赖。

### 9.2 最终设计

采用三层边界：

```text
EODHD client
  只负责 HTTP、缓存、重试和预算
        ↓
EODHD mapper/provider
  负责供应商字段解释和身份映射
        ↓
标准 Parquet contracts
  bars / universe / corporate_actions / delistings
        ↓
特征、标签、训练、评价
```

所有下游模块只依赖标准表。增加新供应商时，应实现 provider adapter，而不是修改模型代码。

## 10. API token、缓存和付费配额的三重约束

### 10.1 证据与问题

- 证据等级：`工程验证暴露`
- 全历史候选约 2 万多只，同时请求 EOD、dividend 和 split，调用量约 6.8 万。
- token 如果进入 YAML、cache key、manifest 或异常日志，就可能被提交到 Git。
- 部分 EODHD endpoint 的一次网络请求可能按多次 API call 计费。

### 10.2 最终设计

安全：

- YAML 只写环境变量名称；
- token 存在 `.env.local`，并由 `.gitignore` 排除；
- cache identity 明确移除 `api_token`；
- manifest 只记录 token 来源名，不记录值。

成本：

- 请求前持久化 reserve 调用预算；
- 同时记录 `network_attempts` 和 `api_calls`；
- 支持 bulk endpoint 的 `call_cost`；
- 达到日预算前主动失败；
- 成功响应落盘缓存，重启后复用。

可恢复性：

- cache key 由 path 和排序后的公开参数哈希得到；
- 写缓存先写临时文件再原子 rename；
- 失败重启不会重复下载已有响应。

- [`src/facdigger/data/providers/eodhd/client.py`](../src/facdigger/data/providers/eodhd/client.py)
- [`tests/unit/data/providers/test_eodhd.py`](../tests/unit/data/providers/test_eodhd.py)
- [`.gitignore`](../.gitignore)

### 10.3 面试讲法

> 对全量金融数据，API adapter 不只是 `requests.get`。我把 secret safety、可恢复缓存和加权配额放在同一个 client 边界里。测试会直接读取缓存文件确认 token 不存在；预算在请求前 reserve，所以进程崩溃最多保守多计，不会因为失败重试突破付费上限。

## 12. IBM PatchTST checkpoint 的跨版本迁移

### 12.1 证据与问题

- 证据等级：`工程验证暴露`
- IBM checkpoint 使用的 PatchTST 配置字段和 state key 来自较早实现；
- 当前 Transformers 的字段名、wrapper prefix 和部分模块名称已经变化；
- 金融模型又替换了 prediction head。

典型差异包括：

- `stride` → `patch_stride`；
- `encoder_layers` → `num_hidden_layers`；
- `encoder_attention_heads` → `num_attention_heads`；
- `w_p` → `embedder.input_embedding`；
- 旧 BatchNorm 子层名称与当前实现不同；
- `module.`、`base_model.`、`model.` 等 wrapper prefix。

### 12.2 为什么不能直接 `load_state_dict(strict=False)`

`strict=False` 只表示“不因 mismatch 抛异常”，不表示迁移成功。最危险的情况是：

- 命令能运行；
- 大部分 encoder 参数没有加载；
- 模型实际接近随机初始化；
- 研究报告却把它标成 E2 迁移学习。

这类错误比显式 crash 更难发现。

### 12.3 最终设计

第一步：配置规范化。

- 把旧字段和新字段映射到 `CanonicalPatchTSTConfig`；
- 明确检查 context length、channel 数、patch、hidden layers、attention、normalization 等；
- 架构不一致时训练前阻断。

第二步：checkpoint → 当前 Transformers source backbone。

- 规范化 state key；
- 按“规范化名称 + exact shape”匹配；
- 计算 loaded parameter numel ratio；
- 未在 allowlist 中的 missing、unexpected、shape mismatch 全部阻断。

第三步：source backbone → 金融 Alpha backbone。

- 再做一次同样的严格迁移；
- 比较完整参数和 buffer 指纹；
- 要求迁移后 target 指纹等于 source；
- 要求迁移后 target 不等于随机初始化。

代码证据：

- [`src/facdigger/models/patchtst_adapter.py`](../src/facdigger/models/patchtst_adapter.py)
- [`src/facdigger/models/patchtst_transfer.py`](../src/facdigger/models/patchtst_transfer.py)
- [`tests/unit/test_patchtst_adapter.py`](../tests/unit/test_patchtst_adapter.py)
- [`tests/unit/models/test_patchtst_transfer.py`](../tests/unit/models/test_patchtst_transfer.py)

### 12.4 面试讲法

> 迁移学习最容易出现“代码不报错，但根本没迁移”的假成功。我没有依赖 `strict=False`，而是做了两段可审计迁移：旧 checkpoint 先装进当前库的同构 backbone，再迁到金融模型。每段都按规范化 key 和精确 shape 匹配，设置参数量比例门槛，并用全模型指纹证明 target 真正等于 source、且不再是随机初始化。

## 13. 缺失值不能只做“补零”

### 13.1 证据与问题

- 证据等级：`工程验证暴露`
- 日频金融特征天然会缺失：新股历史不足、成交量缺失、停牌、rolling window 未成熟。

如果只把 NaN 补成 0：

- 0 可能是合法的收益或标准化值；
- pooling 会把缺失 patch 当作真实观测；
- masked reconstruction 会尝试重建人工填充值；
- 模型可能学到数据管道的缺失模式，而不是价格行为。

### 13.2 最终设计

- window 同时输出 `values` 和 `observed_mask`；
- 缺失值可补 0，但 mask 保留真实观测语义；
- encoder adapter 从 element mask 推导 patch mask 和 channel mask；
- AlphaHead 只在有效 patch 上池化；
- E3 loss 只聚合“被随机 mask 且原本真实 observed”的元素；
- 如果一个 batch 没有有效重建目标，直接报错。

代码证据：

- [`src/facdigger/datasets/window.py`](../src/facdigger/datasets/window.py)
- [`src/facdigger/models/patchtst_alpha.py`](../src/facdigger/models/patchtst_alpha.py)
- [`src/facdigger/models/patchtst_pretrain.py`](../src/facdigger/models/patchtst_pretrain.py)

### 13.3 面试讲法

> 补零只是数值层面的处理，不是语义层面的处理。我让 observed mask 从数据窗口一直传到 patch pooling 和 reconstruction loss。尤其在 E3 中，只有“原本观测到、后来被随机遮挡”的元素才进入 loss，人工补零永远不是重建目标。

## 14. Outer validation 不能参与 early stopping

### 14.1 证据与问题

- 证据等级：`研究审查发现`
- 早期常见训练模式是每个 epoch 看 validation loss 并保存 best checkpoint。

在单次工程实验里很常见，但在本项目的 Walk-forward 比较中，outer validation 用来比较 E0–E3。如果又用它选择 epoch，就已经把比较集用于训练决策。多模型、多 seed、多次迭代后会逐步过拟合 validation。

### 14.2 另一个更隐蔽的泄漏：标签窗口重叠

即使按 `asof_date` 把 Train 尾部 10% 切为 inner selection，前一段最后几天的 `label_end` 仍可能落进 selection 区间。这样 fitting rows 的标签使用了 selection 时间段的价格。

### 14.3 最终设计

- official Train 内部再按日期切尾部 10% 为 `inner_selection`；
- fitting rows 只来自更早的 inner fit；
- purge 所有 `label_end >= inner_selection_start` 的 fitting rows；
- early stopping 和 best checkpoint 只看 inner selection；
- outer validation/test 仅在训练结束后评价；
- manifest 记录 outer validation/test 的训练访问和 checkpoint-selection 访问行数，必须为 0；
- E3 虽然是无监督预训练，也只允许使用 official Train，因为未来分布本身也是信息。

代码证据：

- [`src/facdigger/training/common.py`](../src/facdigger/training/common.py)
- [`src/facdigger/datasets/splits.py`](../src/facdigger/datasets/splits.py)
- [`tests/unit/training/test_common.py`](../tests/unit/training/test_common.py)
- [`tests/unit/training/test_e3_split.py`](../tests/unit/training/test_e3_split.py)

### 14.4 面试讲法

> 我把“validation”拆成了 inner selection 和 outer validation。inner selection 在 Train 内，只负责 early stopping；outer validation 只负责模型比较。切分时不只看 as-of date，还 purge 掉 label end 跨过边界的样本。甚至 E3 的无监督预训练也不能读取未来 validation，因为未来的分布结构本身就是泄漏。

## 15. 训练恢复不是“重新加载 model.pt”

### 15.1 证据与问题

- 证据等级：`工程验证暴露`
- 训练可能运行数小时或更久，必须支持中断恢复。

只保存模型参数会丢失：

- optimizer momentum；
- scheduler 位置；
- GradScaler 状态；
- Python、NumPy、Torch、CUDA RNG；
- 当前 epoch/global step；
- early stopping 历史；
- sampler 顺序和位置。

恢复后虽然“能继续”，但训练轨迹已不同，无法判断 resumed run 是否与不中断运行等价。

### 15.2 最终设计

E1–E3 checkpoint 保存：

- model；
- optimizer；
- scheduler；
- GradScaler；
- epoch/global step；
- best epoch/loss/stale epochs；
- 完整 history；
- RNG states；
- sampler state；
- dataset ID；
- 完整 training protocol hash；
- E2/E3 的 source weights hash；
- 阶段审计。

恢复前检查：

- checkpoint family 正确；
- dataset ID 一致；
- protocol/config hash 一致；
- source weight hash 一致；
- run 状态允许恢复；
- 不能恢复已完成 run。

代码证据：

- [`src/facdigger/training/e1_engine.py`](../src/facdigger/training/e1_engine.py)
- [`src/facdigger/training/e2_engine.py`](../src/facdigger/training/e2_engine.py)
- [`src/facdigger/training/e3_engine.py`](../src/facdigger/training/e3_engine.py)
- [`tests/integration/test_e1_resume.py`](../tests/integration/test_e1_resume.py)
- [`tests/integration/test_e2_resume.py`](../tests/integration/test_e2_resume.py)
- [`tests/integration/test_e3_resume.py`](../tests/integration/test_e3_resume.py)

### 15.3 面试讲法

> 我把 resume 定义成“恢复状态机”，不是“加载模型继续跑”。checkpoint 包括 RNG 和按日期采样器状态，恢复前还绑定 dataset、完整配置和 source checkpoint hash。这样避免拿旧数据的 checkpoint 接到新协议上，生成一个表面能跑、实际不可解释的混合实验。

## 16. 如何证明 FT-0 真冻结、FT-1 真解冻

### 16.1 证据与问题

- 证据等级：`工程验证暴露`
- E2/E3 采用两阶段微调：
  - FT-0：冻结 encoder，只训练 alpha head；
  - FT-1：解冻 encoder 联合训练。

仅检查 `requires_grad` 不够。optimizer 参数组、错误的 `.train()` 切换、BatchNorm buffer 或代码重构都可能让实际变化与预期不同。

### 16.2 最终设计

每个阶段第一次 optimizer step 前后计算：

- encoder 参数和 buffer 的完整指纹；
- alpha head 参数和 buffer 的完整指纹。

硬门禁：

| 阶段 | Encoder | Head |
|---|---|---|
| FT-0 | 必须不变 | 必须变化 |
| FT-1 | 必须变化 | 必须变化 |

如果不符合，训练立即失败，并把阶段审计保存在 checkpoint 和报告中。

代码证据：

- [`src/facdigger/models/patchtst_transfer.py`](../src/facdigger/models/patchtst_transfer.py)
- [`src/facdigger/training/e2_engine.py`](../src/facdigger/training/e2_engine.py)
- [`src/facdigger/training/e3_engine.py`](../src/facdigger/training/e3_engine.py)

### 16.3 面试讲法

> 我没有把冻结策略当成配置声明，而是当成运行时不变量。FT-0 第一步后，encoder 指纹必须完全不变、head 必须变化；FT-1 两者都必须变化。这样能发现 optimizer 参数组配错或 buffer 被更新这类肉眼不容易看出的错误。

## 17. LightGBM 原生运行库冲突：用进程边界隔离

## 18. 数据不足时，中性化不能“勉强给一个结果”

### 18.1 证据与问题

- 证据等级：`研究审查发现`
- 正式目标要求行业和 log float market cap 中性化。
- 当前 EODHD 日线没有可靠的点时行业和流通市值。

如果用今天的行业/市值回填历史，会引入未来信息；如果中性化失败后退回 raw score，却仍把列名叫 neutralized score，会产生错误研究结论。

### 18.2 最终设计

- 评价器只有在暴露存在、样本足够且设计矩阵可用时才计算 residual；
- 不满足条件时 neutralized score 保持 null；
- 记录不可用原因；
- 工程配置关闭：
  - `require_source_research_ready`；
  - `require_neutralized_positive`；
- preflight 明确标记 `research_mode=engineering`；
- 正式研究必须重新开启硬门禁，并补齐点时暴露。

- [`configs/research/m6_eodhd_engineering.yaml`](../configs/research/m6_eodhd_engineering.yaml)

### 18.3 面试讲法

## 19. 重叠收益下，普通 t 检验不可信

### 19.1 证据与问题

- 证据等级：`研究审查发现`
- 标签是 5-session forward return，相邻日期的标签窗口高度重叠。
- 日度 IC、spread 和 paired delta 因此存在序列相关。
- 如果把每天当作独立样本，普通标准误会偏小，t 值偏高。

### 19.2 最终设计

- 先按日期对多个 seed 求均值，避免把 seed 当成独立市场样本；
- fold 内计算 Newey–West / HAC 标准误；
- 另外使用固定 offset 的非重叠样本；
- 同时报告样本数、均值、标准误和 t-stat；
- 模型比较使用相同日期、相同证券键上的 paired delta。

代码证据：

- [`src/facdigger/research/statistics.py`](../src/facdigger/research/statistics.py)
- [`src/facdigger/research/aggregate.py`](../src/facdigger/research/aggregate.py)
- [`tests/unit/research/test_statistics.py`](../tests/unit/research/test_statistics.py)

### 19.3 面试讲法

> 5 日收益每天滚动计算时，相邻标签共享 4 天，不能把每一天当 IID。我同时做 HAC 和固定 offset 非重叠检验，而且先按日期聚合 seed。这样 seed 是模型随机性的重复，不会被错误地当成更多市场样本。

## 20. Final holdout 不能靠“大家自觉不看”

### 20.1 证据与问题

- 证据等级：`研究审查发现`
- 多模型、多 seed、多个 fold 的开发过程会反复查看 validation。
- 如果 test 也能随命令轻易运行，它最终会参与调参，失去 holdout 含义。

### 20.2 最终设计

validation 阶段结束后冻结：

- resolved research config；
- fold plan；
- 完整 cell matrix；
- 每个 validation 结果；
- 研究报告 hash。

解封 final holdout 时：

- 必须显式提供 `--unlock-final-holdout`；
- 重新校验冻结哈希；
- 只运行最后一折的 test cells；
- 已有输出不覆盖；
- test 结果与 validation 结果分层保存。

代码证据：

- [`src/facdigger/research/runner.py`](../src/facdigger/research/runner.py)
- [`src/facdigger/research/preflight.py`](../src/facdigger/research/preflight.py)
- [`tests/integration/test_m6_runner.py`](../tests/integration/test_m6_runner.py)

### 20.3 面试讲法

> Holdout 不是一个 `split="test"` 字符串，而是一套访问控制。我的 runner 先冻结 validation 配置、cell matrix 和报告哈希；只有显式解封并通过哈希复核，才运行最终 test。这样至少能让“什么时候看过 test”在工程上可追踪。

## 21. 训练完成不等于 checkpoint 可回放

### 21.1 证据与问题

- 证据等级：`工程验证暴露`
- 训练脚本在内存中直接预测成功，只能证明当时的 Python 对象可用。
- 它不能证明磁盘 checkpoint、预处理 sidecar、resolved config 和 dataset 能独立重建相同结果。

### 21.2 最终设计

独立 `predict` 流程：

1. 读取 source run manifest；
2. 校验 resolved config hash；
3. 校验 dataset manifest hash；
4. 校验 checkpoint hash；
5. E0 LightGBM 额外校验 preprocessing sidecar；
6. 在新流程中重建 E0–E3 模型；
7. 重新预测；
8. 默认与原始 raw score 做固定容差核对；
9. 原子生成 replay manifest、predictions、factors、metrics 和 report；
10. 不覆盖已有 replay。

代码证据：

- [`src/facdigger/inference/runner.py`](../src/facdigger/inference/runner.py)
- [`src/facdigger/evaluation/runner.py`](../src/facdigger/evaluation/runner.py)
- [`tests/unit/inference/test_runner.py`](../tests/unit/inference/test_runner.py)
- [`tests/integration/test_lightgbm_replay.py`](../tests/integration/test_lightgbm_replay.py)

### 21.3 面试讲法

> 我把 replay 当作发布门禁：训练进程退出后，用磁盘上的 manifest、配置、dataset 和 checkpoint 在独立路径重建模型，并要求分数与原输出一致。这样才能证明 checkpoint 是真正的产物，而不是训练脚本顺手保存的一份不完整文件。

## 22. 因子导出必须与标签彻底分离

### 22.1 证据与问题

- 证据等级：`工程验证暴露`
- 训练用 sample index 通常包含 target 和 split。
- 如果直接复用它生成“最新因子”，很容易把未来收益或评价字段一起写入生产文件。

### 22.2 最终设计

- dataset snapshot 单独生成 `inference_index.parquet`；
- inference index 不包含 target 和 split；
- 覆盖所有具备完整 context 的 eligible 日期，包括尚未形成未来收益的最新日期；
- `factors.parquet` 明确禁止 target；
- 写入：
  - raw score；
  - 可用时的 neutralized score；
  - model/checkpoint/dataset lineage；
  - `signal_available=after_close`；
  - `earliest_execution=next_session_open`。

独立 `evaluate` 命令再从不可变快照按键关联 target，而不是让 target 跟随因子文件传播。

代码证据：

- [`src/facdigger/datasets/index.py`](../src/facdigger/datasets/index.py)
- [`src/facdigger/data/snapshots.py`](../src/facdigger/data/snapshots.py)
- [`src/facdigger/inference/runner.py`](../src/facdigger/inference/runner.py)

### 22.3 面试讲法

> 我没有用训练 sample index 直接导出生产因子，而是建了一个物理上不含 target/split 的 inference index。评价时再从不可变快照按键取标签。这个边界既防止未来字段泄漏，也让最新尚无 t+5 收益的日期能够正常出信号。

## 23. 一些贯穿全项目的设计原则

### 23.1 Fail closed，而不是 silent fallback

适合阻断的情况：

- 主键重复；
- checkpoint hash 不一致；
- source weights 加载比例不足；
- 未授权 shape mismatch；
- outer validation 被训练访问；
- 恢复训练的数据或协议不一致；
- 因子覆盖率不足。

适合降级并标记的情况：

- 点时行业/市值不可用；
- 退市收益只能插值；
- 当前 source 只能用于 engineering 模式。

判断标准是：这个缺口会让输出“含义错误”，还是仅让输出“结论权限下降”。

### 23.2 把研究假设写进数据血缘

不仅记录代码版本，还记录：

- 股票池发现规则；
- liquidity ranking；
- adjustment basis；
- delisting imputation；
- identity quality；
- source readiness；
- 中性化可用性；
- signal timing。

### 23.3 区分工程可运行和研究可信

项目允许：

- smoke 验证接口；
- paid pilot 验证吞吐和资源；
- engineering M6 验证完整闭环。

但这些模式不会自动升级成正式研究结论。正式结论仍需要：

- 完整历史动态股票池；
- 真实或更可信的 delisting return；
- 点时行业和流通市值；
- 目标 GPU 正式门禁；
- 完整 walk-forward、多 seed 和 final holdout。

### 23.4 可观察性应该是下一轮工程重点

当前 EODHD 全量采集主要通过 cache 文件数和 budget state 观察，训练主要通过每个 epoch 写入的 `last.pt` 观察。命令行尚未持续输出：

- 当前 symbol / 总 symbol；
- cache hit ratio；
- 下载速率和 ETA；
- epoch / batch progress；
- train/inner-selection loss；
- GPU memory。

下一轮应增加结构化日志或 `tqdm`，同时保留机器可读 JSONL，避免只靠文件数监控。

## 24. 面试问答速记

### Q1：这个项目最难的地方是什么？

推荐回答：

> 难点不是 PatchTST forward，而是如何证明研究链路没有“看起来能跑、其实不可信”。例如真实全量 EODHD 数据出现同 ISIN 重复键时，根因同时包含 ticker alias 和被错标的权证，不能粗暴 dedup；迁移学习中 `strict=False` 也会让随机模型伪装成迁移成功。所以我把数据契约、权重审计、split 访问审计和回放哈希做成硬门禁。

### Q2：为什么不直接用 ticker 做证券 ID？

> ticker 是显示代码，不是稳定身份。公司会改 ticker，直接使用 ticker 会切断历史。项目优先使用 ISIN，同时保留 provider symbol；但 ISIN 也不能盲信，所以先过滤共享 ISIN 的衍生工具，再对真实 alias 做确定性历史合并。

### Q3：如何防止时间泄漏？

> 有三层：数据层按 known-at 和全市场 session 生成标签；训练层只在 Train 内做 inner selection，并 purge label-end 跨边界样本；研究层 outer validation 不参与 checkpoint 选择，final holdout 需要冻结哈希后显式解封。E3 无监督预训练也不能使用未来 validation 分布。

### Q4：如何证明 E2 真的使用了预训练权重？

> 不是看 `load_state_dict` 是否返回。我先把旧 checkpoint 字段和 key 规范化，再分两段加载；每段按名称和 shape 审计，计算 loaded numel ratio，拒绝未授权 mismatch。最后用全 backbone 指纹证明迁移后 target 与 source 完全一致，同时与随机初始化不同。

### Q5：为什么允许退市收益插值？

> 因为完全删除跨退市样本会形成更隐蔽、更系统性的乐观偏差。插值不是最终答案，而是显式的工程假设：逐行标记、进入 manifest、降低 research readiness，并要求敏感性分析。正式结论仍应替换为真实 delisting return。

### Q6：为什么中性化做不出来却不直接删除功能？

> 功能实现本身是有价值的，但当前 source 缺点时行业和流通市值。删除功能会丢失未来扩展接口；伪造暴露又不可信。因此 evaluator 保留中性化能力，不满足条件时输出 null 和原因，工程配置关闭硬门禁，正式配置必须补数据后重新开启。

### Q7：你如何保证实验可复现？

> dataset snapshot、resolved config、source checkpoint 和训练 checkpoint 都有内容哈希；checkpoint 保存 optimizer、scheduler、scaler、RNG 和 sampler；训练后还会在独立路径从磁盘回放并核对分数。可复现不是“seed 固定”一个开关，而是数据、状态和产物的完整绑定。

### Q8：如果重新做一次，最优先改什么？

> 第一是接入可靠的 security master 和真实 delisting return，减少规则型身份判断；第二是补点时行业和流通市值，让中性化恢复正式门禁；第三是给长时间采集和训练增加结构化实时进度；第四是在目标 CUDA GPU 上完成正式吞吐和 FP16 门禁。

## 25. STAR 讲述模板

### 案例 A：EODHD 身份冲突

**Situation**

全量历史采集从 smoke/pilot 扩展到 2 万多只 active + delisted 候选后，标准表唯一键检查报同一 `security_id + trade_date` 重复。

**Task**

既要恢复采集，又不能用会破坏 ticker 历史连续性的临时去重。

**Action**

检查真实 metadata 和 EOD payload，区分：

- 被错标为 Common Stock 的 warrants/units；
- 同一公司的 old/current ticker aliases。

然后实现：

- 名称、后缀、peer ticker 衍生品过滤；
- ISIN 稳定身份；
- 非重叠历史保留；
- 重叠时 active → latest coverage → symbol 的确定性优先级；
- batch 内外双重合并；
- audit 字段和回归测试。

**Result**

全项目 71 项测试通过，已有 API 缓存被复用，真实采集恢复。最终全量数据质量仍待采集结束后审计，因此不能把“进程恢复”表述成“正式实验已经成功”。

### 案例 B：PatchTST 迁移假成功

**Situation**

IBM checkpoint 与当前 Transformers 在配置字段和 state key 上存在版本差异，直接 `strict=False` 可以运行但无法证明加载了多少 encoder。

**Task**

确保 E2 和 E3 的“迁移”是可验证事实，而不是实验标签。

**Action**

- 建立 canonical config；
- 规范化历史 key；
- 两段权重迁移；
- exact-shape 和 loaded-numel 审计；
- mismatch allowlist；
- source/target/random 三方指纹验证；
- FT-0/FT-1 首步参数变化审计。

**Result**

任何未经授权的 mismatch 或加载比例不足都会在训练前失败，run 保存完整 weight load report，E2/E3 的初始化来源可以被独立复核。

### 案例 C：防止 validation 被用作训练集

**Situation**

E0–E3 需要在同一 outer validation 上比较。如果每个模型都用它 early stop，多轮开发会对 validation 过拟合。

**Task**

既保留 early stopping，又保持 outer validation 的比较效力。

**Action**

- Train 内按日期建立 inner selection；
- purge 标签窗口跨边界样本；
- checkpoint 只看 inner selection；
- outer validation/test 训练访问计数必须为 0；
- validation 完成后冻结研究哈希；
- final holdout 显式解封。

**Result**

训练选择、模型比较和最终 holdout 的职责被分离，研究报告能审计每个 split 被谁、在什么阶段访问。

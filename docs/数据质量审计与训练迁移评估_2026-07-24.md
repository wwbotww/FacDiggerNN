## 4. P0-1：全市场日历被假交易日污染

bars 日期并不是可靠的交易所 session calendar。

审计使用 2010–2025 年 NYSE 常规闭市规则，并包含：

- Good Friday；
- MLK、Presidents Day、Memorial Day；
- Independence Day、Labor Day、Thanksgiving、Christmas；
- 2022 年起 Juneteenth；
- Hurricane Sandy；
- George H. W. Bush national day of mourning。

结果：

| 项目 | 数量 |
|---|---:|
| 预期常规 session | 4,025 |
| bars union 日期 | 4,164 |
| 供应商额外日期 | 139 |
| 缺失常规 session | 0 |
| 额外日期中 bars 少于 100 | 139 |

典型额外日期：

- 2010-01-18：MLK，只有 2 个 bars；
- 2010-04-02：Good Friday，只有 1 个 bar；
- 2012-12-25：Christmas，只有 1 个 bar；
- 2023-01-02：New Year observed，只有 1 个 bar；
- 2024-03-29：Good Friday，只有 1 个 bar。

当前 universe 使用所有证券 bars 日期的 union 构造 calendar。少量错误 bar 因此把闭市日变成全市场 session。

### 连锁影响

ADV20 使用 20 行 rolling mean。每个假交易日对绝大部分证券都是 null，因此接下来的 19 个真实 session 也无法满足 `min_samples=20`。

这解释了异常的 daily eligible 分布：

| 指标 | 当前值 |
|---|---:|
| eligible median | 3 |
| eligible mean | 375.4 |
| eligible max | 1,000 |
| 1,000 股票 session | 1,559 |
| eligible 为 0 的 session | 812 |
| 首次出现 eligible 后仍为 0 | 561 |

正式修复应引入显式 XNYS/XNAS 交易日历，而不能再使用 bars union。

## 5. P0-2：ticker 复用和混合行情产生数量级跳变

合格股票中存在 919 行单日 adjusted price 变化超过 10 倍，涉及 47 个稳定身份。

其中多数属于 `provider_symbol_fallback`。典型例子：

### `LAN.US`

同一时间序列在约 `0.16` 和 `8,000–9,000` 之间交替，单日 log return 接近 `±11`。

### `PGS.US`

同一时间序列在约 `3–70`、后来约 `20,000` 的价格间跳变，单日 log return 可超过 `13`。

这些并不是合理的普通股收益。它们更像是：

- ticker 被不同国家或不同时期的证券复用；
- provider endpoint 混入多个 instrument；
- metadata 没有 ISIN 时无法拆分稳定身份；
- 错误价格乘成交量后被误判为高流动性。

当前 outlier 统计：

| 检查 | 数量 |
|---|---:|
| eligible 单日绝对变化超过 100% | 1,297 |
| eligible 单日变化超过 10 倍 | 919 |
| 涉及证券 | 47 |
| eligible 且 adjustment factor > 1,000 | 1,027 |
| eligible 且 volume = 0 | 3,645 |

不能只对 feature winsorize，因为错误同时影响：

- ADV20 和每日 top-1000；
- forward return label；
- benchmark return；
- delisting terminal value。

修复至少需要：

1. 对 provider-symbol fallback 增加 ticker-reuse 断点检测；
2. 对单日价格比、货币/价格量级和 metadata identity 设置 source gate；
3. 对异常证券做隔离或拆分，而不是把 return 截断后继续保留错误流动性。

## 6. P0-3：公司行动 alias 重复和冲突

公司行动表通过了基础数值契约，但没有事件唯一性约束。

深度审计结果：

| 项目 | 数量 |
|---|---:|
| 完全相同语义事件的重复组 | 2,890 |
| 多余重复行 | 3,052 |
| 同 security/date/type 的冲突组 | 1,389 |
| 单事件最多 alias copies | 3 |

完全重复例子：

```text
GEN.US / NLOK.US / SYMC.US
JW-A.US / JWA.US / WLY.US
GCI.US / GCI_OLD.US / TDAY.US
```

冲突例子：

```text
RPT.US / AJX.US
同一 ISIN、同一 ex-date、同为 dividend，但 cash amount 分别为 1.50 和 0.25。
```

这说明“相同 ISIN 即同一可无条件合并证券”仍不够安全。公司行动应使用与 bars 相同的 alias 优先级，并对冲突事件 fail closed。

## 7. P0-4：退市生命周期与 alias 合并不一致

4 个 delisting 的 `last_trade_date` 与合并后 bars 的真实最后日期不同。

典型原因：

- 某个 old alias 被标记为 delisted；
- 同一 ISIN 的 active alias 仍有更晚行情；
- universe 用 `is_delisted_source.max()` 把整个稳定身份标成 eventually delisted；
- delisting terminal price 却可能取 old alias 的早期价格。

这会直接污染跨退市标签，必须在构建快照前修复。

正确语义应按稳定身份聚合 metadata：

- 任一可信 active alias 存在时，不能因 old alias 而把整个身份判定为退市；
- 只有所有 alias 均结束且不存在 active listing 时，才生成 delisting；
- last trade 必须与最终合并 bars 的最后有效日期一致。

## 9. P0-6：窗口存储内存放大（已修复）

修复前，`SnapshotWindowDataset` 会为每个 split 重新构造：

- 全量 7 通道 float32 values；
- observed mask；
- Python date list；
- date → row position dictionary。

当前构造数量：

| 模型 | 完整 feature block 副本 |
|---|---:|
| E1 | train-fit、inner-selection、evaluation，共 3 份 |
| E2 | 3 份 |
| E3 | pretrain、pretrain-selection、train-fit、inner-selection、evaluation，共 5 份 |

按约 2,500 万 feature rows 粗略估算：

- 单份 NumPy values + mask 约 0.9 GB；
- Python dates 和 position dictionaries 约 2–3 GB；
- 再加 Polars features、sample indexes、模型和临时数组；
- E1/E2 总内存可能超过 16 GB；
- E3 明显可能超过 24–32 GB。

2026-07-27 已完成以下修复：

- E1、E2、E3 每个进程只构造一个 `SecurityFeatureStore`；
- train、selection、evaluation 等 split dataset 共享同一组 values 和 observed mask；
- 日期从 Python `date` list 改为紧凑的 NumPy `datetime64[D]`；
- 删除逐行 `date → position` Python dictionary，改用有序日期二分定位；
- sample location 从 Python tuple list 改为两个 `int32` NumPy 数组；
- 特征 store 建立后从训练 frames 中移除原始 Polars features 引用，降低稳定态峰值。

这消除了 E1/E2 的三份和 E3 的五份完整 feature block 复制。仍未实现 mmap/Arrow lazy
reader，因此首次构造 store 和 snapshot build 仍需要足够系统内存；正式目标机建议至少
32 GB RAM，并在全量 M6 前以一个 cell 测量峰值。

## 11. RTX 2070 训练预估

以下估计假设：

- 标准 RTX 2070，约 8 GB VRAM；
- CUDA FP16 可用；
- 系统内存至少 32 GB；
- 使用已完成的共享 feature store；
- batch 64 起步，随后测试 128/256。

在目标电脑实测前，只能给区间估计。对于当前 1.31M 参数 PatchTST，合理预期是 Mac CPU 的约 6–18 倍吞吐：

| 项目 | RTX 2070 粗估 |
|---|---:|
| 训练吞吐 | 400–1,200 samples/s |
| 单 epoch | 0.5–1.8 小时 |
| E1 常见单 cell | 5–22 小时 |

| E3 常见单 cell | 11–32 小时 |
| 完整 3-fold × 3-seed E0–E3 | 约 1–4 周 |

主要不确定性：

- Windows native 与 WSL2 的 I/O；
- batch 64 是否充分利用 GPU；
- 系统 RAM；
- snapshot loader 是否先完成共享存储优化；

准确估计方法是在 RTX 电脑上跑：

1. 100–500 个 warmup steps；
2. 再测 1,000 steps；
3. 记录 samples/s、VRAM peak 和 DataLoader wait；
4. 用正式 fold 的 batch 数外推。

## 12. 数据迁移到 RTX 2070 电脑

### 12.1 可移植性结论

迁移方便。

以下格式都跨 macOS、Windows 和 Linux：

- Parquet；
- JSON manifest；
- YAML config；
- Python source；
- PyTorch checkpoint。

项目配置使用相对路径，因此目录结构一致时无需修改数据内容。

### 12.2 推荐迁移时机

当前 bronze 仍有 P0 质量问题。

推荐：

1. Mac 上修复标准化逻辑；
2. 从本地 API cache 重新生成 bronze；
3. 审计通过；
4. 构建不可变 snapshot；
5. 再把 snapshot、bronze 和代码同步到 RTX 电脑。

这样 RTX 电脑不需要 EODHD token，也不需要重新下载。

### 12.3 必须与可选内容

训练最小集合：

```text
FacDiggerNN repository
data/snapshots/<dataset_id>/
IBM PatchTST source checkpoint（本机缓存或重新下载）
```

推荐同时保存：

```text
data/bronze/eodhd_us_historical_liquid/
```

仅在 RTX 电脑也要重新 ingest 时才需要：

```text
data/cache/eodhd_historical_liquid/   # 3.2 GB，可选
```

不要复制：

```text
.env.local
```

除非明确需要让 RTX 电脑访问 EODHD，并且使用安全方式单独配置 token。

### 12.4 迁移方式

推荐顺序：

1. 局域网 SSH/SCP 到 WSL2；
2. 外置 SSD；
3. SMB 共享；
4. 压缩包或云盘。

Parquet 已经压缩，再使用 gzip 收益很小。建议只打包不二次压缩：

```bash
tar -cf FacDiggerNN-data.tar \
  data/bronze/eodhd_us_historical_liquid \
  data/snapshots/<dataset_id>

shasum -a 256 FacDiggerNN-data.tar
```

Windows PowerShell 校验：

```powershell
Get-FileHash .\FacDiggerNN-data.tar -Algorithm SHA256
tar -xf .\FacDiggerNN-data.tar
```

如果使用 WSL2，建议把 repository 和 snapshot 放在 WSL2 Linux 文件系统中，而不是长期放在 `/mnt/c`，以减少大量小随机读取的 I/O 开销。

### 12.5 RTX 电脑最小验收

```bash
uv sync --extra data --extra model --extra baseline --extra dev
uv run facdigger doctor
```

必须确认：

```text
cuda_available: true
cuda_device_name: RTX 2070
```

然后执行：

1. PatchTST checkpoint compatibility probe；
2. batch 64 的 CUDA/FP16 smoke；
3. checkpoint save/resume；
4. 1000-step throughput benchmark；
5. 根据 VRAM 再尝试 batch 128 或 256。

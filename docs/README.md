稳定技术文档不追加某次作业的时间线。作业进度、精确参数、全量指标和哈希以已有机器产物、
冻结 manifest 与收据为准；实验记录只摘录支持解释的主表和定位，不复制整份运行台账。
当前判断只在概览维护，历史判断和替代理由留在对应实验记录，不另建 STATUS/TODO/ROADMAP 等入口。

## 后续维护规则

1. **实验启动前**，在 `实验记录/` 按研究问题或明确对照集合记录设计：名称/日期/状态、
   假设、对照与改变项、共同固定条件、事前评价和结果判读、依赖及证据位置；冻结实际计划和配置。
   新实验引用共同协议，避免手抄完整参数；一个集合的 seed/fold/补跑不各建一份文档。
2. **实验结束后**，在同一记录补主表、观察、解释、不能证明的内容、局限和决策理由，
   同时保留阴性结果及失败原因。代码版本、冻结计划/配置、产物目录、汇总文件和产生正式结论的
   分析脚本及其输入定位必须可追溯；无法核实的事前判读写“当时未记录”，不追溯补成预登记。
3. **运行中**，只有协议变化、关键故障或重要结论修正需要更新长期文档；协议变更另列日期和理由，
   不覆盖原设计。日常排队、运行进度、普通测试增加和提交记录留在机器记录，不反复写长篇复盘。
4. **新结论或方向改变**，更新研究概览中的判断、证据缺口、前三项工作和索引；在实验记录保留
   原判断及被替代理由。计划的原始设计与当前执行状态分开，不用已见结果改写当时条件。
5. **工程问题**，仅对影响正确性、兼容性、恢复、数据边界或研究解释的重要问题维护
   [复盘索引](项目关键问题与修复复盘.md)及相应主题文件，保留根因、修复、回归与限制。
   复盘引用科学结果，实验记录引用故障细节，各自只保留理解所需背景。
6. **稳定技术文档**，改接口更新对应职责文档；配置是参数默认值依据，文档解释架构、协议、方法和
   边界。持续运维步骤写运维指南，某次发布写有日期的交接，不向所有 README 复制说明。
7. 明确区分 F/S/V/holdout、旧/修复后协议、原生 S-best/诊断重评分、观察/已确认原因，
   以及曾提出/已确认/已实现/执行完成。作业完成、工程验收和因子有效分别写日期及证据范围。
8. **历史与迁移**，归档只补明确勘误或导航，不维护第二套当前状态；移动/合并时检查路径、锚点、
   命令与关键结果，保护已有未提交内容。不移动或改写原始实验目录、checkpoint、预测、日志、
   冻结 manifest，也不把秘密或生成产物加入文档变更。

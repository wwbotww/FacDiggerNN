## 5. 旗舰案例：EODHD 同一 ISIN 导致重复主键

### 5.1 证据与影响

- 证据等级：`实际运行故障`
- 触发命令：

```bash
uv run facdigger data ingest \
  --config configs/data/eodhd_historical_liquid.yaml
```

- 真实错误：

```text
bars_daily has duplicate keys ['security_id', 'trade_date']
```

- 已观察到的冲突包括：

```text
eodhd:isin:KYG330331201
eodhd:isin:US00258Y1047
eodhd:isin:KYG330321061
```

这个错误由标准表契约在写入 Parquet 前阻断。如果没有唯一键门禁，重复记录会进入 rolling feature、标签和横截面排序，后续结果可能仍能生成，但一个证券会在同一天出现两次，属于“静默污染”。

### 5.2 根因不是单一的“脏数据”

真实数据检查发现存在两类完全不同的冲突。

第一类是 EODHD 元数据的证券类型泄漏：

```text
AACT      Ares Acquisition Corporation II
AACT-WT   Ares Acquisition Corporation II WT
```

二者被标为 `Common Stock`，并共享 `KYG330331201`，但价格显然属于普通股和权证两个不同工具，不能按同一证券合并。

第二类是真实 ticker 迁移或别名：

```text
ABX
ABL
```

二者共享 `US00258Y1047`，EOD endpoint 返回大量重叠历史；同一天的 OHLC 基本相同，但 volume 可能有轻微舍入差异。这一类应该保持证券历史连续，而不能被拆成两个独立公司。

### 5.3 为什么几个直觉方案都不够好

方案一：直接把 `security_id` 改成 ticker。

- 优点：立即消除重复键。
- 问题：ticker 会变化；公司改名或换代码后历史被切断。
- 后果：rolling feature、上市天数、退市判断和训练窗口全部出现人为断点。

方案二：遇到重复行就 `unique(keep="first")`。

- 优点：代码最短。
- 问题：结果取决于 API 顺序和 batch 顺序，不具确定性。
- 问题：可能把权证价格当成普通股，也可能丢掉旧 ticker 独有的早期历史。

方案三：所有相同 ISIN 都无条件合并。

- 优点：保持 ticker 迁移连续。
- 问题：EODHD 的权证、单位和 rights 可能与普通股共享 ISIN 或被错误标型。
- 后果：会把价格量级完全不同的证券拼成一条时间序列。

### 5.4 最终采用的两层修复

第一层：候选发现阶段修正明显的证券类型泄漏。

- 保留 provider 的 `Type` 初筛；
- 再检查名称中的 `warrant`、`unit`、`right`；
- 检查 `-WT`、`-UN`、`-RT` 等衍生代码后缀；
- 对无分隔符的 `W/U/R` 后缀，仅在存在同名基础 ticker peer 时排除，降低误杀普通公司的风险；
- 在 manifest selection audit 中记录排除数量。

第二层：对真正的 ticker alias 合并历史。

- 稳定身份仍优先使用 ISIN；
- 非重叠日期全部保留，避免丢失旧 ticker 独有历史；
- 重叠日期优先当前 active alias；
- 其次优先历史覆盖终点更晚的 alias；
- 最后按 provider symbol 排序，保证确定性；
- batch 内和所有 batch concat 后都执行一次，避免同一 ISIN 跨 250-symbol batch 时再次冲突；
- manifest 记录 `overlapping_alias_rows_resolved`。

### 5.5 验证

- 新增 ticker alias 重叠测试；
- 新增衍生工具过滤测试；
- 原 EODHD adapter 测试全部通过；
- 全项目 72 项测试通过；
- 复用已有 977 个 API 缓存响应恢复真实采集，API 调用继续增长，原重复键没有在相同位置再次触发。

代码证据：

- [`src/facdigger/data/providers/eodhd/universe.py`](../../src/facdigger/data/providers/eodhd/universe.py)
- [`src/facdigger/data/providers/eodhd/mapper.py`](../../src/facdigger/data/providers/eodhd/mapper.py)
- [`src/facdigger/data/providers/eodhd/provider.py`](../../src/facdigger/data/providers/eodhd/provider.py)
- [`tests/unit/data/providers/test_eodhd.py`](../../tests/unit/data/providers/test_eodhd.py)

### 5.6 面试讲法

> 我在第一次全量下载 2 万多只美股历史时，标准表唯一键门禁拦住了重复的 `(security_id, trade_date)`。继续看真实 payload 后发现这不是普通 dedup：一部分是 ticker rename，应该合并；另一部分是 EODHD 把权证和 unit 错标成 Common Stock，而且它们还共享 ISIN，绝对不能合并。我最后做了两层设计：先用名称、后缀和 peer ticker 修正衍生品泄漏，再对真正的 alias 保留非重叠历史，并用 active、覆盖终点和 ticker 做确定性重叠选择。这个方案没有退化成用 ticker 当主键，也不会因 API 返回顺序改变结果。

### 5.7 尚存局限

- ISIN 本身也可能存在供应商错误；
- 规则型衍生品识别不能替代完整 security master；
- 最终全量 Parquet 和 selection audit 仍需在采集完成后检查；
- 更成熟的方案是接入带 `effective_from/effective_to` 的 ticker mapping 和 instrument type 主数据。

### 5.8 后续真实故障：零价占位和不一致 OHLC

DATA-01 修复后，采集从 977 个缓存响应继续到 1190 个，随后再次被数据契约阻断：

```text
bars_daily has 24 invalid OHLCV/adjustment rows
```

扫描当时已有缓存，共发现 15 个 symbol、33 行非法观测，主要分为：

1. 全部 OHLC、adjusted close 和 volume 都是 0 的 provider 占位记录；
2. `low > close` 或 `high < close` 的内部不一致 OHLC；
3. 前一版过滤规则漏掉的 `AAGRW`、`ACABW`、`ACII-U`、`ACHR-WS` 等衍生工具。

真实样例：

```text
ACAQ.US  2023-11-06  open=0 high=0 low=0 close=0 adjusted_close=0 volume=0
ACII-U.US 2021-02-12 open=10.95 high=11.25 low=10.895 close=10.85
ACHR-WS.US 2024-06-28 open=0.334 high=0.355 low=0.334 close=0.3725
```

这里没有采用以下“修复”：

- 把 0 价格替换为前值：这会凭空制造可交易价格和成交；
- 强行令 `high=max(open, high, close)`：这会掩盖供应商错误；
- 关闭 OHLCV contract：这会让错误进入特征和标签；
- 遇到坏行删除整只股票：这会不必要地损失其他有效历史。

最终处理分两层：

- 扩展衍生工具识别，覆盖显式 `-U/-WS`，以及 Nasdaq 常见的第五字符 `W/U/R` 和 `_OLD` alias；
- provider 映射前检查 finite、正价格、OHLC 包含关系、非负 volume 和正复权因子；
- 只丢弃非法“观测行”，不修造价格；
- 后续 universe 全市场 session 网格仍保留该日期，并将缺失观测显式表示为 halt/missing；
- manifest 记录 `invalid_eod_rows_dropped`、相关 symbols 和 warning。

这次修复新增 provider placeholder 测试，项目测试总数增至 72。

面试时可概括为：

> 数据清洗不是让 contract 不报错，而是决定错误信息应该怎样进入研究语义。对 0 价占位，我没有 forward-fill 或修改 high/low，而是把它当成“不存在可信 bar”。删除坏观测后，市场 session 仍在 universe grid 中保留，因此下游看到的是显式 missing/halt，而不是一根伪造 K 线。

## 6. 从“当前最活跃 100 只”升级为历史动态股票池

### 6.1 证据与问题

- 证据等级：`研究审查发现`
- 早期 paid pilot 从“今天仍 active 的股票”中按当前 200 日平均成交量选 100 只，再回看历史。

工程上它很方便，但研究上有两个偏差：

1. 存活偏差：历史上退市的公司完全不在样本中；
2. 历史前视偏差：用今天的流动性决定多年前的股票池。

这会系统性高估策略表现，尤其会忽略破产、并购和低流动性退出样本。

### 6.2 最终设计

- 候选发现同时读取 active 和 delisted 普通股；
- 候选阶段不使用当前流动性排名；
- 对每只证券恢复上市区间内的全市场 session 网格；
- 仅用截至当日的 trailing ADV20；
- 每个历史交易日独立选取最多 1000 只；
- 记录候选规模、active/delisted 数量、排名规则和 research readiness。

这里的关键拆分是：

```text
候选发现：谁在历史上可能存在
        ↓
点时 eligibility：某只股票在某一天是否可交易、是否足够流动
```

两者不能合并成“先用今天的数据选一批股票，再回测”。

代码证据：

- [`configs/data/eodhd_historical_liquid.yaml`](../../configs/data/eodhd_historical_liquid.yaml)
- [`src/facdigger/data/providers/eodhd/universe.py`](../../src/facdigger/data/providers/eodhd/universe.py)
- [`src/facdigger/data/providers/eodhd/mapper.py`](../../src/facdigger/data/providers/eodhd/mapper.py)

### 6.3 面试讲法

> 最开始的 100 股票 pilot 只用于证明系统能跑通。我没有把它包装成正式回测，因为它先看了今天谁还活着、谁现在最流动，再回到历史。正式协议把 candidate discovery 和 daily eligibility 分开：candidate 纳入 active 和 delisted，daily eligibility 只使用当时能知道的 trailing ADV20。这样工程 pilot 和研究结论的边界是显式的。

## 7. 标签终点不能按“个股第 5 根 K 线”推进

### 7.1 证据与问题

- 证据等级：`研究审查发现`
- 目标是预测全市场交易日 `t+5` 的 next-open 到 next-open 超额收益。

如果按每只股票自身的第 5 个后续观测推进，停牌一天的股票会把标签终点移到市场 `t+6`。不同股票的“5 日收益”实际对应不同持有期，横截面不可比，也产生对停牌状态的选择偏差。

### 7.2 最终设计

- 从所有日线构建全市场 session 日历；
- `label_start` 和 `label_end` 通过市场 session 位移得到；
- 股票某个 session 缺少 bar 时，在 universe grid 中显式标记 `is_halted`；
- 标签不能偷偷寻找更晚的一根个股 K 线替代目标日；
- 若窗口跨退市，则进入退市 terminal value 分支。

代码证据：

- [`src/facdigger/labels/forward_return.py`](../../src/facdigger/labels/forward_return.py)
- [`src/facdigger/data/providers/eodhd/mapper.py`](../../src/facdigger/data/providers/eodhd/mapper.py)
- [`tests/integration/test_dataset_pipeline.py`](../../tests/integration/test_dataset_pipeline.py)

### 7.3 面试讲法

> 一个容易忽略的问题是 horizon 到底是“市场过去 5 个 session”还是“这只股票出现 5 根 K 线”。后者遇到停牌会错位。我把 universe 做成证券 × 市场 session 网格，标签终点由全市场日历定义，缺失 bar 明确标成停牌或缺失，不允许向后偷找价格。

## 8. 没有真实退市收益时，如何避免静默删除失败样本

### 8.1 证据与问题

- 证据等级：`研究审查发现`
- 当前 EODHD 套餐能提供 delisted 列表，但没有足够可靠的退市原因和 terminal return。

如果一只股票在标签窗口内退市，`label_end` 没有正常价格。最简单的实现会得到 null 并删除样本，而这些样本通常表现更差，删除它们会形成系统性乐观偏差。

### 8.2 最终设计

工程阶段采用明确、版本化的交易所惩罚假设：

| 交易所 | 默认 `delisting_return` |
|---|---:|
| Nasdaq | -55% |
| NYSE / NYSE American | -30% |
| 未知 | -50% |

具体约束：

- 插值表逐行标记 `is_imputed=true`；
- 记录 `imputation_method` 和 exchange；
- source manifest 写入完整政策和警告；
- 标签窗口跨退市时，用最后有效价格乘 `(1 + delisting_return)`；
- 数据仍标记为不满足正式 research readiness；
- 实验文档要求对惩罚参数做敏感性分析。

这不是声称插值“正确”，而是把未知问题从静默删除变成显式、可复核的假设。

代码证据：

- [`src/facdigger/data/providers/eodhd/mapper.py`](../../src/facdigger/data/providers/eodhd/mapper.py)
- [`src/facdigger/labels/forward_return.py`](../../src/facdigger/labels/forward_return.py)
- [`src/facdigger/data/contracts.py`](../../src/facdigger/data/contracts.py)

### 8.3 面试讲法

> 我没有用插值假装获得了真实退市收益。我的目标是先修复“坏样本静默消失”这个更危险的问题：把惩罚假设写进数据行和 manifest，并降低 source readiness。正式研究仍需要 CRSP 一类真实 delisting return；当前结果只能做工程验证和敏感性分析。

## 9. 数据源适配：避免把 EODHD 字段写进整个项目

### 9.1 证据与问题

- 证据等级：`工程验证暴露`
- EODHD 使用 `adjusted_close`、`Isin`、`Code`、`Exchange` 等供应商字段；后续更换供应商时字段和语义都会变化。

如果 feature、label 和 model 直接读取这些字段，数据源会成为全项目的结构性依赖。

### 9.2 最终设计

采用三层边界：

```text
EODHD client
  只负责 HTTP、缓存、重试和预算
        ↓
EODHD mapper/provider
  负责供应商字段解释和身份映射
        ↓
标准 Parquet contracts
  bars / universe / corporate_actions / delistings
        ↓
特征、标签、训练、评价
```

所有下游模块只依赖标准表。增加新供应商时，应实现 provider adapter，而不是修改模型代码。

代码证据：

- [`src/facdigger/data/providers/base.py`](../../src/facdigger/data/providers/base.py)
- [`src/facdigger/data/providers/registry.py`](../../src/facdigger/data/providers/registry.py)
- [`src/facdigger/data/contracts.py`](../../src/facdigger/data/contracts.py)
- [`src/facdigger/data/providers/eodhd/`](../../src/facdigger/data/providers/eodhd)

### 9.3 巧妙点

供应商特有字段没有完全丢弃，而是作为审计列保留，例如：

- `provider_symbol`；
- `identity_quality`；
- `exchange_source`；
- `trade_status_quality`；
- `adjustment_basis`。

这样既保持下游接口中立，又没有牺牲问题追踪能力。

## 10. API token、缓存和付费配额的三重约束

### 10.1 证据与问题

- 证据等级：`工程验证暴露`
- 全历史候选约 2 万多只，同时请求 EOD、dividend 和 split，调用量约 6.8 万。
- token 如果进入 YAML、cache key、manifest 或异常日志，就可能被提交到 Git。
- 部分 EODHD endpoint 的一次网络请求可能按多次 API call 计费。

### 10.2 最终设计

安全：

- YAML 只写环境变量名称；
- token 存在 `.env.local`，并由 `.gitignore` 排除；
- cache identity 明确移除 `api_token`；
- manifest 只记录 token 来源名，不记录值。

成本：

- 请求前持久化 reserve 调用预算；
- 同时记录 `network_attempts` 和 `api_calls`；
- 支持 bulk endpoint 的 `call_cost`；
- 达到日预算前主动失败；
- 成功响应落盘缓存，重启后复用。

可恢复性：

- cache key 由 path 和排序后的公开参数哈希得到；
- 写缓存先写临时文件再原子 rename；
- 失败重启不会重复下载已有响应。

代码证据：

- [`src/facdigger/data/providers/eodhd/client.py`](../../src/facdigger/data/providers/eodhd/client.py)
- [`tests/unit/data/providers/test_eodhd.py`](../../tests/unit/data/providers/test_eodhd.py)
- [`.gitignore`](../../.gitignore)

### 10.3 面试讲法

> 对全量金融数据，API adapter 不只是 `requests.get`。我把 secret safety、可恢复缓存和加权配额放在同一个 client 边界里。测试会直接读取缓存文件确认 token 不存在；预算在请求前 reserve，所以进程崩溃最多保守多计，不会因为失败重试突破付费上限。

## 11. 不可变快照：防止“同一个路径、不同一份数据”

### 11.1 证据与问题

- 证据等级：`工程验证暴露`
- 训练配置可能仍指向同一个 `bars_daily.parquet` 路径，但文件内容已经被重新采集覆盖。
- 仅记录路径无法证明某个 checkpoint 使用了哪一份数据。

### 11.2 最终设计

快照构建时固化：

- 标准化数据；
- features、labels、sample index；
- sample metadata；
- 不含 label/split 的 inference index；
- source manifest；
- 每个文件的 SHA-256；
- dataset ID 和 schema version。

训练 manifest 再记录：

- dataset manifest hash；
- resolved config hash；
- source checkpoint hash；
- 代码/环境信息；
- split 访问审计。

恢复或回放时，哈希不一致直接阻断。

代码证据：

- [`src/facdigger/data/snapshots.py`](../../src/facdigger/data/snapshots.py)
- [`src/facdigger/experiments/manifest.py`](../../src/facdigger/experiments/manifest.py)
- [`src/facdigger/inference/runner.py`](../../src/facdigger/inference/runner.py)

### 11.3 面试讲法

> 我不把“配置文件路径相同”当作可复现。数据、配置和 checkpoint 都有内容哈希，run manifest 记录三者的绑定关系。这样可以回答：这个分数究竟来自哪份原始 source manifest、哪份快照、哪个 checkpoint，而不是只能说“应该是那个目录”。

## 13. 缺失值不能只做“补零”

### 13.1 证据与问题

- 证据等级：`工程验证暴露`
- 日频金融特征天然会缺失：新股历史不足、成交量缺失、停牌、rolling window 未成熟。

如果只把 NaN 补成 0：

- 0 可能是合法的收益或标准化值；
- pooling 会把缺失 patch 当作真实观测；
- masked reconstruction 会尝试重建人工填充值；
- 模型可能学到数据管道的缺失模式，而不是价格行为。

### 13.2 最终设计

- window 同时输出 `values` 和 `observed_mask`；
- 缺失值可补 0，但 mask 保留真实观测语义；
- encoder adapter 从 element mask 推导 patch mask 和 channel mask；
- AlphaHead 只在有效 patch 上池化；
- E3 loss 只聚合“被随机 mask 且原本真实 observed”的元素；
- 如果一个 batch 没有有效重建目标，直接报错。

代码证据：

- [`src/facdigger/datasets/window.py`](../../src/facdigger/datasets/window.py)
- [`src/facdigger/models/patchtst_alpha.py`](../../src/facdigger/models/patchtst_alpha.py)
- [`src/facdigger/models/patchtst_pretrain.py`](../../src/facdigger/models/patchtst_pretrain.py)

### 13.3 面试讲法

> 补零只是数值层面的处理，不是语义层面的处理。我让 observed mask 从数据窗口一直传到 patch pooling 和 reconstruction loss。尤其在 E3 中，只有“原本观测到、后来被随机遮挡”的元素才进入 loss，人工补零永远不是重建目标。

## 28. DATA-07～11：基础契约通过后，深审计仍发现 P0 数据污染

- 日期：2026-07-24
- 阶段：正式实验前全量数据审计与修复
- 证据等级：`研究审查发现` + `工程验证暴露`
- 数据：EODHD All World，US active + delisted，2010-01-01 至 2025-12-31
- 影响范围：市场日历、ADV20、动态 top-1000、forward label、公司行动、退市标签和
  M6 输入选择

### 28.1 为什么“契约通过”仍然不等于数据正确

第一次全量标准化完成后：

- `(security_id, trade_date)` 唯一；
- OHLC、volume、adjustment factor 数值合法；
- eligible 行具备 close、ADV20 和 rank；
- 文件哈希与 manifest 一致。

但深审计发现：

1. bars 日期并集包含交易所闭市日；
2. provider-symbol fallback 和错误 ISIN alias 中存在不同证券混合历史；
3. 公司行动在 alias 合并后仍有重复和冲突；
4. old alias 的 delisted 标志覆盖了仍 active 的 current alias；
5. M6 仍指向旧 100 股票 pilot，且旧 manifest 没有来源质量证明。

这次问题说明基础 contract 只能回答“字段和局部不变量是否合法”，无法独立回答“整条
时间序列是不是同一个证券”“这个日期是不是市场 session”以及“两个公司行动是否代表
同一个经济事件”。正式实验前必须再做跨表、跨时间和来源语义审计。

### 28.2 DATA-07：假交易日如何放大成股票池系统性缺失

旧实现从所有 bars 的日期并集生成市场 calendar。审计发现闭市日上偶尔存在 1～数根
供应商异常 bar；一根错误 bar 就会把该日扩展成所有证券的 session。ADV20 又按 20 行
窗口并要求 20 个有效值，因此一个伪 session 会让大量证券随后约 19 个真实 session 的
ADV20 变成 null。

旧数据的直接表现是：

- daily eligible 中位数只有 3；
- 812 个日期没有任何 eligible 股票；
- 首次出现 eligible 后仍有 561 个零股票日期。

最终设计没有使用“每日 bars 数低于某阈值就删除”这种依赖当前股票池规模的启发式，而
是在 provider 边界引入版本化的 `US_EQUITIES_REGULAR` 日历：

- 递归节假日：MLK、Washington's Birthday、Good Friday、Memorial Day、
  Independence Day、Labor Day、Thanksgiving、Christmas；
- 2022 年起 Juneteenth；
- Hurricane Sandy；
- Reagan、Ford、George H. W. Bush、Carter national day of mourning；
- 半日交易仍视为 session；
- New Year 落在周六时不错误地把前一周五删除。

审计初稿曾按近似规则得到 4,025 个 session，正式实现补入 2025-01-09 Carter
national day of mourning 后，2010–2025 的正确实现计数为 4,024。真实重建删除了
140 个闭市日期上的 876 根 bars；修复后 4,024 个 session 全部至少有一根市场 bar，
不存在闭市日残留。

### 28.3 DATA-08：为什么没有直接 winsorize 万倍收益

旧数据中可观察到：

- `LAN.US` 在约 0.16 与 8,000～9,000 之间切换；
- `PGS.US` 在个位数、几十和约 20,000 之间切换；
- 相同 ISIN 的不同 alias 在同一天可能给出不同价格。

如果只在 feature 层 winsorize return，错误的 raw close × volume 仍会进入 ADV20 和
top-1000，错误价格也仍会进入 benchmark、forward return 和退市终值。因此最终门禁在
alias 合并**之前**检查两类证据：

1. 同一 `security_id + trade_date` 的多个 alias，adjusted price 相差超过 5%；
2. 同一身份相邻正式 session 的 adjusted price 比值超过 10 倍或低于 1/10。

命中任一条件时整条身份被隔离；不截断收益、不修改价格、不把冲突 alias 随机选一个。
第一次只在已经合并的旧 bronze 上回放时识别出 1,093 个身份；在原始 alias 合并前执行
后又识别出额外冲突，真实重建最终隔离 1,293/13,176 个身份，即 9.81%。这也证明门禁
必须放在 consolidation 前。

项目设置 10% 系统性损失上限：若下一批来源数据需要隔离的身份比例超过该值，采集直接
失败并要求人工检查，而不是悄悄接受更大范围的数据损失。修复后的 bars 保留 11,883 个
证券、21,750,078 行；剩余相邻 session 超过 10 倍的 adjusted-price 跳变为 0。

被否决的方案：

- 直接截断 return：无法修复股票池和标签；
- 仅删除异常日：断点两侧仍可能属于不同证券；
- 所有相同 ISIN 无条件合并：真实数据已经证明供应商 ISIN 也会冲突；
- 改用 ticker 作为永久 ID：会切断正常 ticker rename 的历史；
- 无上限地自动隔离：来源格式发生系统性变化时会静默丢掉大部分市场。

### 28.4 DATA-09：公司行动冲突为什么选择“整组不用”

旧公司行动表虽然数值合法，但存在 exact alias copies，以及同一
`security_id + ex_date + action_type` 下 cash amount 或 split factor 不一致的事件。

最终处理顺序是：

1. 对相同经济条款的 alias copies 去重；
2. active alias 优先，其次按 known-at 和 provider symbol 确定性选择审计行；
3. 若同一事件 key 的经济条款不一致，整组排除；
4. 已被价格身份门禁隔离的证券，其公司行动也一并排除。

“整组排除”会损失少量事件，但优于选择一个无法证实的 dividend 或 split。重建后公司
行动为 162,302 行；事件 exact duplicate groups 和 event conflict groups 均为 0。
manifest 记录：随隔离身份删除 12,773 行、exact alias 删除 808 行、94 个冲突组
（188 行）整组删除。

### 28.5 DATA-10：退市生命周期不能用布尔值 `max()`

旧实现对同一稳定身份的 alias 使用：

```python
is_delisted_source.max()
```

只要 old ticker 被标记为 delisted，即使 current ticker 仍 active，整个身份也会被标记
为 eventually delisted。随后退市表又可能从 old alias 取较早 last trade，导致 bars 与
delistings 不一致。

修复后的优先级是：

- 任一 current alias 明确 active，则稳定身份不因 old alias 被判退市；
- 只有所有合并 alias 都是 delisted 时，才进入退市生命周期；
- `last_trade_date` 从合并后的 universe 生命周期取得，而不是过滤 old alias bars；
- delist date 使用最后交易日后的第一个正式 market session。

真实重建后 delistings 为 6,588 行，`last_trade_date` 与 bars 最后日期不一致数量从 4
降为 0。退市收益仍是交易所惩罚插值，不因此升级为正式研究数据。

### 28.6 DATA-11：让旧数据无法“误通过”

只修 provider 不够：旧 bronze 文件仍然存在，而且基础 schema contract 会通过。为避免
用户或自动化流程误建快照，新增三层来源质量证明：

1. ingestion manifest 写入 calendar 名称/版本、过滤数量、隔离身份、公司行动处理和
   `quality.gate`；
2. provider 将专属质量结果转换为版本化 `facdigger.standard_parquet` 通用证明；
   `data validate` 和 dataset snapshot 要求证明 `status == passed`，并逐文件核对
   SHA-256，防止质量证明与被替换的 Parquet 脱钩；
3. M6 preflight 独立检查同一通用证明，即使工程模式关闭 `research_ready` 硬要求，也
   不能绕过基础数据质量。下游去除供应商分支的后续修复见 DATA-12。

数据集名从 `eodhd_us_historical_liquid_v1` 升为 `v2`，使旧快照语义失效；M6 base
dataset 同时从旧 `eodhd_all_world_pilot.yaml` 修正为
`eodhd_historical_liquid.yaml`。

## 51. DATA-08 / PROD-07：先去重再审计，真实冲突就会“消失”

### 51.1 原始证据与根因

2026-09-20 当前生产准备的原始缓存抽查中，已取得的 458 个交易日包含 41 个存在冲突的
ISIN、11,838 个冲突身份/日期组：同一 ISIN 的多个 ticker 对同一日期返回的复权价相差超过
既有 5% 阈值。例如旧/新别名的复权更新范围不同，也有明显不同报价序列。这不等于所有
同 ticker/ISIN 的历史都错误，但不能在未检查时直接择一拼接。

历史 ingestion 原来先运行 `quarantine_suspicious_identities` 再 `consolidate_bars`；daily
adapter 却先 consolidate，等到 production store 的质量检查时，一组只剩一行，别名冲突
已经不可见。最终 Parquet 格式和哈希可以全部正确，但原始来源质量证据已经丢失。这是
**真实 API 审计暴露的检查顺序缺陷**，不是模型训练损失函数问题，也不是 XOM 十只交付映射
自身的错误。本次发现时没有因子发布或交易。

原始抽查证据：本机 `artifacts/production_readiness/20260920/raw_alias_audit_partial.json`。
最终完整检查以同目录 `raw_alias_audit.json` 为准，不把部分扫描当作全部历史结论。

### 51.2 修复与验证

daily provider 内增加小型共用 `_quality_checked_bars`，用于 bulk revision 和定向复权回填：
先检查原始日历/身份，再合并一致别名。它复用已有门禁和阈值，不新增 identity alias 或
“优先采用看起来正常的价格”规则。原始质量审计随 revision 写入 manifest，store 仍检查
跨修订边界；不因先过滤原始响应就删除后者。无法信任的定向复权替换不能冒充成功回填。

此外，真实隔离审计包含 Polars 的 date 对象。历史 writer 曾用 `default=str` 隐式处理，
而 production writer 用严格 JSON，导致只有出现真实异常样本时才会序列化失败。修复位于
审计的产生处：例子日期明确转换成 ISO 字符串；没有给整个 writer 加任意对象字符串化兜底。
已有持久化 JSON 的日期格式不变。

回归覆盖一致别名、冲突先于去重、超出隔离比例仍失败、不可信定向回填不得保留旧历史冒充
修复、真实隔离审计能严格 JSON 写入。微型测试为了容纳两只证券中的一只隔离，使用局部
50% fixture 阈值；真实生产仍为既有 10%，没有为跑通本次数据放宽配置。

发现问题后停止未完成初始化，保留原始缓存，从空生产 store 重新按修复后的通路续取。
不修改旧训练数据、不手动剔除原始文件、不混入已完成 FactorBatch。初始化端到端耗时必须
包含这次暂停/修复，续跑耗时单独列出，不能冒充无缓存冷启动的性能。

### 53.2 修复与取舍

- 源隔离分类保留原因、证券、日期和有限示例。供应商 endpoint 成交量细小差异也没有在
  本轮静默改值，严格隔离并留证；后续是否采用精度等价规则须有独立证据和测试。

关键设计不是“捕获异常继续跑”，而是把负面质量事实变成可恢复、可追溯的状态，并让正确
层级的门禁决定整批是否可用。牺牲的是恢复隔离证券需要完整复核，收益是不会把短窗口的

能否生产。三只自身评分恢复仍需独立历史连续性复核；不改训练快照、release 或旧交付。

## 61. MARKET-CALENDAR-01：没有合格证券的 session 也属于市场历史

### 根因与证据

2026-09-28，修复预训练证券末端读取后的最大 fold 作业 `3663796` 通过数据集构造，随后
报错 `market context is shorter than 512 sessions at 2012-07-17`。CPU 诊断 `3663797`
确认来源日历有 4,024 个 session，市场特征却仅 3,773 行，从 2010-12-31 才开始；所需
个股历史始于 2010-01-04，失败日期只有 389 行市场历史。原市场特征先过滤 eligible 再
聚合，删除了预热期中没有任何合格股票的 251 个 session。加载器正确拒绝短窗口，根因
在特征构造，而非下载缺失、GPU 或 context_length 设置。

同一错误也会压缩中间没有 eligible 股票的日期，使 rolling_std 的“20 日”跨过真实缺失
session。新增预热期和内部空日期回归在旧实现均失败，不能靠缩短上下文、删早期样本、
降低上市时长门槛或向前填价格来修复。

### 修复与兼容边界

市场横截面聚合仍只用当时 eligible 股票；聚合结果对齐完整特征交易日历后再计算滚动量。
空日期保留 null/false mask，由既有窗口读取器生成零占位；不存在的观测不参与统计。
样本与未来日期不被移动，未来资格不回写历史，整个输入没有 eligible 样本仍报错。

金融训练快照使用 schema v5 生成新内容身份，防止同配置误命中旧市场日历缓存。其文件布局
不变；价量/E1—E3 快照保持 v4，旧金融 v4 仍按原哈希读取、搬运和校验，绝不原地修补。
修复后的新训练必须重建到新的准备目录，并重新做资源准入；不允许给已绑定 run 换数据。
无需重新下载或改变原始 bronze、来源证明、split、上下文、股票池或模型超参数。

训练与推理共用这一个特征构造器。新金融推理快照将
`market_calendar_policy: all_feature_sessions` 纳入已有内容身份，避免复用缺日期的旧缓存；
旧不可变推理快照仍可验证读取。ModelRelease、scaler、checkpoint 和 FactorBatch 格式不变，
价量推理身份也不变；本次不部署或重启每日生产服务，不替换生产 release。

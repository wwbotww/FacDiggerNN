## 21. 训练完成不等于 checkpoint 可回放

### 21.1 证据与问题

- 证据等级：`工程验证暴露`
- 训练脚本在内存中直接预测成功，只能证明当时的 Python 对象可用。
- 它不能证明磁盘 checkpoint、预处理 sidecar、resolved config 和 dataset 能独立重建相同结果。

### 21.2 最终设计

独立 `predict` 流程：

1. 读取 source run manifest；
2. 校验 resolved config hash；
3. 校验 dataset manifest hash；
4. 校验 checkpoint hash；
5. E0 LightGBM 额外校验 preprocessing sidecar；
6. 在新流程中重建 E0–E3 模型；
7. 重新预测；
8. 默认与原始 raw score 做固定容差核对；
9. 原子生成 replay manifest、predictions、metrics 和 report；
10. 不覆盖已有 replay。

代码证据：

- [`src/facdigger/inference/runner.py`](../../src/facdigger/inference/runner.py)
- [`src/facdigger/evaluation/runner.py`](../../src/facdigger/evaluation/runner.py)
- [`tests/unit/inference/test_runner.py`](../../tests/unit/inference/test_runner.py)
- [`tests/integration/test_lightgbm_replay.py`](../../tests/integration/test_lightgbm_replay.py)

### 21.3 面试讲法

> 我把 replay 当作发布门禁：训练进程退出后，用磁盘上的 manifest、配置、dataset 和 checkpoint 在独立路径重建模型，并要求分数与原输出一致。这样才能证明 checkpoint 是真正的产物，而不是训练脚本顺手保存的一份不完整文件。

## 22. 因子导出必须与标签彻底分离

### 22.1 证据与问题

- 证据等级：`工程验证暴露`
- 训练用 sample index 通常包含 target 和 split。
- 如果直接复用它生成“最新因子”，很容易把未来收益或评价字段一起写入生产文件。

### 22.2 最终设计

- dataset snapshot 单独生成 `inference_index.parquet`；
- inference index 不包含 target 和 split；
- 覆盖所有具备完整 context 的 eligible 日期，包括尚未形成未来收益的最新日期；
- 研究 `predict` 不再同时写另一种 factors；跨项目输出只能经过严格 FactorBatch publisher；
- FactorBatch 固定五列，显式绑定 model/checkpoint/dataset lineage 与可用时间。

独立 `evaluate` 命令再从不可变快照按键关联 target，而不是让 target 跟随因子文件传播。

代码证据：

- [`src/facdigger/datasets/index.py`](../../src/facdigger/datasets/index.py)
- [`src/facdigger/data/snapshots.py`](../../src/facdigger/data/snapshots.py)
- [`src/facdigger/inference/runner.py`](../../src/facdigger/inference/runner.py)

### 22.3 面试讲法

> 我没有用训练 sample index 直接导出生产因子，而是建了一个物理上不含 target/split 的 inference index。评价时再从不可变快照按键取标签。这个边界既防止未来字段泄漏，也让最新尚无 t+5 收益的日期能够正常出信号。

## 38. INFER-03 / REPRO-02：因子文件哈希不能代表完整交付语义

### 38.1 证据与影响

- 证据等级：`工程验证暴露`。
- 在设计 FacDiggerNN 与交易系统的文件边界时，早期方案令 `delivery_id` 只等于
  `factors.parquet` 的 SHA-256。
- 这样同一份因子文件可以被重新搭配不同的模型 release、输入 snapshot、来源 run 或
  可用时间，而目录身份仍保持不变。文件字节没有损坏，但消费者看到的谱系和交易语义
  已被替换，单纯检查 Parquet 哈希无法发现。
- 原始训练 run 里的 checkpoint、resolved config、训练 snapshot scaler 和 manifest
  也分散在不同目录。只复制 checkpoint 不能证明推理采用的是训练时 scaler，更不能把
  当前完整日 objective 与旧 Huber/chunked 权重区分开。

### 38.2 最终设计

项目增加两层独立、不可变的契约：

1. `facdigger.model_release` 严格契约只供 FacDiggerNN 内部推理使用。release 要求 source
   run 记录有效的 clean commit，发布工具自身也必须 clean；发布命令可在后续提交执行，但
   release 始终保留训练 run 的
   原始 commit，避免把发布代码身份冒充训练代码身份；复制 checkpoint、resolved
   config、冻结 scaler、训练 dataset manifest、source run manifest 和提取出的 checkpoint
   protocol，并逐文件记录 SHA-256/bytes；新生成的 E0—E3 run 还在 manifest 中直接绑定
   训练时 scaler 与原始 predictions 的 SHA-256，旧 run 缺少任一证据、scaler 后来被替换或
   predictions 被重新序列化时拒绝 release；
   EODHD 来源若仍含 provider-symbol fallback 身份也拒绝 release，避免 ticker 被交易系统
   误当成稳定主身份；
2. PatchTST release 读取 checkpoint 本身，要求 schema v3、objective v2、
   `optimization_protocol.unit=complete_date` 及训练 dataset ID 一致。由此旧 Huber、v1
   chunked ranking 和无法证明完整日协议的权重不能被误发布。当前明确只发布 E1—E3；
   E0 tabular preprocessing 需要独立兼容契约，不能通过宽泛 allowlist 假装已支持；
3. `facdigger.factor_batch` 严格契约是唯一跨项目边界。Parquet 固定五列，严格空值、
   类型、排序和主键；manifest 记录 source/model/input/time/coverage/artifact；
4. `artifact.sha256` 仍只表示 Parquet 文件完整性，但 `delivery_id` 改为除 `created_at`
   外整个规范 manifest 身份的 SHA-256。模型、输入、时间或覆盖语义发生变化都会产生新的
   delivery；创建时间变化不会破坏同一输入的幂等性；
5. 生产者先在隐藏同级临时目录写 Parquet，完成读取级契约校验和哈希后最后写 manifest，
   再原子 rename。已存在同 ID 目录时先完整重验，绝不静默覆盖。

### 38.3 验证与边界

单元测试覆盖：相同输入在不同创建时间下得到相同 release/delivery ID；只修改 model
语义即产生不同 delivery；非法 nullable 规则、乱序、source/universe 语义冲突被拒绝；
修改 manifest 模型身份或 release scaler 后读取失败；source run 或发布工具工作树 dirty 时
不能创建 release；发布工具运行在后续 clean commit 时仍保留原训练 commit。

后续阶段已经补齐生产侧闭环：新增与训练 snapshot 分离的 target-free inference snapshot，
只复用 ModelRelease 的冻结 scaler，不生成 label/split；快照保存完整 delivery universe，
并把原始 eligibility 与“已有完整 context window”取交集。`facdigger signal` 改为只接收
E3 ModelRelease 和与其特征契约完全一致的 inference snapshot，单次只发布一个 as-of 日期，
最终调用同一 FactorBatch publisher。训练 dataset ID 与输入 snapshot ID 分开记录。

这个实现修正了一个容易忽略的生产问题：原始股票池 eligible 并不保证新上市股票已累积
512 日窗口。若直接拿原始 eligible 做覆盖率分母，这些股票永远没有 score，会把正常批次
误判为漏预测；若静默丢掉，又无法区分 eligibility 变化和生产漏数。交集语义让它们作为
`eligible=false, score=null` 明确交付，同时仍保留完整候选横截面。

### 38.4 面试版讲法

> 我最初看到的设计是“因子 Parquet 的哈希就是交付 ID”，但文件完整不等于语义完整：
> 同一个分数文件可以被换成另一套模型或可用时间 manifest，消费者仍认为是同一批次。
> 所以我把 Parquet 哈希降为 artifact 身份，再让 delivery ID 覆盖模型 release、输入、时间、
> 覆盖率和 artifact 的完整规范语义。同时做了内部 ModelRelease，把 checkpoint、配置、
> scaler、训练快照和 Git commit 绑定，并读取 checkpoint 协议拒绝旧目标权重。这样文件
> 传递保持简单，但研究身份和交易语义都不能被静默替换。

## 39. INFER-04：训练快照不能冒充新交易日推理快照

### 39.1 证据与影响

- 证据等级：`工程验证暴露`。
- 旧 signal runner 要求推理 snapshot ID 和训练 dataset ID 完全相等，因此无法在新交易日
  使用已冻结模型；复用训练快照还会把 label/split 产物带入日常路径。
- 若直接复用训练 snapshot builder，它会重新 fit scaler，使同一个 checkpoint 在不同日期
  使用不同输入尺度。
- 原始 universe 的 `eligible=true` 只表达股票池规则；新上市股票可能尚不足 context
  length，不能被模型打分。直接把原始 eligible 当作覆盖率分母会制造假漏数。

### 39.2 最终设计与验证

新增独立的 inference snapshot builder：它只读取标准 bars/universe，严格验证 ModelRelease，
加载 release 内冻结 scaler，生成 features、target-free inference index 和完整 delivery
universe；不执行 label、split 或 scaler fit。snapshot ID 绑定输入文件、release 特征契约和
scaler 身份，所有产物再次校验哈希。

收尾审计又移除了 signal 路径对整份 features 的重复加载：数据模块现在集中验证 snapshot
语义、全部声明文件哈希、无额外文件、identity policy，以及 inference index 与 delivery
eligibility 的逐键一致性；runner 只把轻量 index/universe 常驻内存，再按目标日期所需窗口
投影读取 features。这既避免两套验证逻辑漂移，也保留了 16 GB 机器上的内存边界。

delivery eligibility 定义为“source eligible 且已有完整模型窗口”。因此不能评分的候选证券
仍保留在 FactorBatch 中，但明确为 `eligible=false, score=null`。集成测试从 E3 训练、release、
inference snapshot 一直跑到 FactorBatch；另有回归测试把 scaler fit 替换成必失败函数，并
逐值比较相同输入区间的训练/推理 features，证明推理构建不会误走训练拟合路径且冻结 scaler
结果完全一致。

收尾检查还发现 `latest` 若从 inference index 取最大日期，会在最新候选交易日没有任何可评分
窗口时静默回退到旧日期。现改为从完整 delivery universe 取最新日期：候选日期不存在则失败，
当日全体不可评分则发布显式无信号批次，避免陈旧分数被误当作当天信号。

## 40. INFER-05：只有一个跨项目因子格式，回放输入必须绑定到 release

### 40.1 证据与影响

- 证据等级：`工程验证暴露`。
- 旧研究 `predict` 会额外写一份与生产 FactorBatch schema 不同的 `factors.parquet`，导致
  “因子文件”有两种含义；交易项目一旦兼容两种输入，target/研究字段隔离和覆盖语义就会
  逐渐分叉。
- 仅检查 predictions 表内 `model_id/checkpoint_hash/dataset_id` 仍不充分：这些都是可编辑
  文本，不能证明分数文件确实来自受审 run。

### 40.2 最终设计与验证

`predict` 回归为纯研究回放，只保存 predictions、metrics 和 report。历史隔离联调使用
`factor-batch from-predictions`：ModelRelease 创建时要求 source run manifest 绑定原始
`predictions.parquet` 的 SHA-256；适配器先验证 release 全部产物，再逐字节核对传入文件，
然后使用与日常 signal 相同的 `build_factor_frame` 和原子 publisher。输出明确标记
`evaluation_predictions/eligible_scored_cross_section`，不能冒充完整候选横截面。

单元测试覆盖原始文件成功转换、target 不进入五列输出，以及任何 predictions 字节变化都会
被拒绝；publisher 故障注入还证明 manifest 写入失败时隐藏临时目录会被清理，不留下可见
半成品。

旧 `artifacts2` 采用修复前的 objective/checkpoint/scaler 绑定协议，不能安全生成当前
ModelRelease，因此不能为了联调而加 legacy bypass。下一轮完整日 E3 实验完成后才能生成
受审回放批次。

## 41. PROD-01：调度时间不是简单的“每天跑一次”

### 41.1 暴露的问题

- 证据等级：`工程验证暴露`。
- 生产约束要求交易日 D 收盘后 19:00 ET 首次执行、30 分钟重试，到下一 regular session
  09:30 ET 截止；只允许发布 D，禁止沿用旧因子。
- 初版日历实现把“当前时刻早于当天 19:00”统一映射到上一交易日。这在下一开盘前是正确的，
  但周一 10:00—19:00 已超过周五截止，如果仍把周五作为当前目标，会不断重复处理一个已
  失效窗口，也掩盖当天 D 尚未到期的状态。
- `signal --asof latest` 适合人工命令，却不能作为生产规则；只要 source 中存在旧日期，就有
  把陈旧分数包装成新交付的风险。

### 41.2 最终设计与验证

状态机明确分成三段：下一开盘前仍处理上一交易日；当天开盘后到 19:00 返回当天
`not_due`；19:00 后只处理当天 D。SQLite 以 target date 为主键，固定 release ID、attempt、
next retry、snapshot/delivery ID 和终态。若上一目标在进入当天 `not_due` 前仍未完成，先标记
`expired`，绝不把它作为回退因子。

runner 所有生产调用都显式传 `asof=D`。FactorBatch 在隐藏临时目录写完并完成校验后、原子
rename 前再次调用 cutoff guard；长时间数据下载或推理跨过 09:30 时不会发布。服务使用
America/New_York zoneinfo，不按宿主本地时区猜测 DST；Docker 安装 tzdata。

回归测试覆盖交易日开盘前/后/19:00、周末延续窗口、过期终态、30 分钟精确重试、已发布
幂等和同一目标禁止切 release。没有真实运行过付费 API 与完整 E3 production tick，因此这
是正式上线前的工程门禁，不伪装成线上事故。

## 42. PROD-02：日常修订不是简单 append

### 42.1 暴露的问题

- 证据等级：`工程验证暴露`。
- EODHD bulk EOD 给出 adjusted close。拆分或分红确认后，`adjusted_close/close` 可能改变
  过去多日甚至整个可见历史的复权尺度。
- 若每日任务只覆盖最近 10 个 session，再把这 10 日覆盖到旧表，窗口边界会出现人为断裂；
  PatchTST 的收益、gap、range 和 vol20 会被污染，但表的唯一键和 OHLC 合法性仍可能通过。

### 42.2 最终设计与验证

正常路径使用 exchange bulk endpoint 一次拉一个 session，最近 10 日共约 1000 个加权 API
units，而不是为全股票逐只请求。合并前对重叠 `(security_id, trade_date)` 比较 adj factor；
变化证券如果新 revision 没覆盖 production hot store 起点，抛出专用
`AdjustmentBackfillRequired`。orchestrator 只对涉及的 provider symbols 调个股 EOD endpoint，
从 hot store 起点回填至 D，再重新执行合并、regular calendar、alias/身份隔离、极端相邻复权
收益和目标日覆盖门禁。

provider request log 必须证明所有 bulk/targeted EOD 响应是 fresh network data；生产配置强制
`refresh=true, cache_ttl_hours=0`。symbol-list 缓存策略不参与价格发布证明。单测用一个正常
窗口和一个复权因子变化证券验证：短 revision 被拒绝，显式标记过的完整 targeted history
通过，且 manifest 记录受影响身份和请求审计。

## 43. PROD-03：把全历史做成每日 immutable revision 会耗尽磁盘

> 演进提示：本案例保留当时从全量存储改成热窗口的过程；其中“目标日 universe”的早期设计随后由 §47 改为热窗口内历史逐日 universe。现行实现以[每日生产运维](../每日生产运维.md)为准。

### 43.1 暴露的问题

- 证据等级：`工程验证暴露`。
- 初版 source revision 每日复制完整历史 bars，并重建全历史 security-session universe；推理
  snapshot 也为所有候选保存整段历史特征。对数千万 bars，这会把一次合理的原子发布变成
  每日数 GB 复制，长期保留 10 份 snapshot 更不可接受。
- 训练快照必须不可变，但这不意味着可重建的日常 source 也要永久保留所有历史版本。

### 43.2 最终设计与验证

生产 store 与训练数据职责拆开：bootstrap 只读已审历史 bronze，截取
`release.context_length + 20` 个 session 的 bars 和最新一日 universe。以后 source revision
继续保持同样 hot window，并只保留 CURRENT 和上一版，提供原子切换与最小恢复窗口；训练
bronze、`data/snapshots/` 和 `data/walk_forward_snapshots/` 从不修改。`listed_days` 从上一
目标日递推，避免窗口裁剪把老股票每天重置成“新上市”。

实现复核还发现，初版为内部 source revision 计算全量语义哈希，并一度试图用分块列式
哈希降低内存。复审后确认这个 revision 只是生产 hot store 的内部原子状态标识，可重建、
不是跨系统契约，因此不应伪装成内容寻址产物。最终删除了两种全表语义哈希方案，改用不透明
UUID 作为 revision ID。Parquet 写入后的文件 SHA-256 仍保留，因为它用于读取时的损坏/篡改检测，
与内部状态命名是两个职责。

目标日 inference builder 从 hot bars 只筛 D 的 eligible 身份，动态生成近 512 日的 session
网格，再复用既有 feature/scaler/index 逻辑；delivery universe 仍是 D 的完整候选横截面。
ledger 先记录 published，常驻服务随后删除超过最近 10 个日期的 inference snapshot；清理
失败不会改变交付终态。FactorBatch 无清理入口，永久保留。回归测试检查 hot bars 的日期上限、source revision 只留两版、目标日 snapshot 只含 D
的 index/universe，且训练 snapshot root 配置会被拒绝。

### 43.3 面试版讲法

> 我一开始为了原子性把每日 source 设计成不可变全量 revision，但算一下规模就发现这会
> 每天复制全历史，属于用研究数据的保留策略套生产缓存。后来我把“必须不可变的训练快照”
> 和“可重建的生产 hot store”分开：训练永不改，生产只留模型上下文加特征 warm-up、当前和
> 上一版；每天的对外交付 FactorBatch 才永久保留。这样没有牺牲可审计交付，又把存储从随
> 历史长度和天数双重增长，收敛到固定窗口。

## 44. INFER-06：全历史回测不能循环伪装成每日生产信号

### 44.1 暴露的问题

- 证据等级：`工程验证暴露`。
- 现有 `signal --asof D` 的职责是发布一个生产语义的完整候选横截面。若为数千个历史日期
  写 shell 循环，会反复验证 release、加载 checkpoint 和构建模型，吞吐很差；任一日期中断后
  也没有“哪些日期构成同一完整导出”的权威状态。
- 更关键的是，每个结果都会标为 `signal_inference`。HeyBoss 允许这种来源进入人工 paper
  边界，而固定 2024/2025 模型回看更早历史显然含参数和 scaler 的未来信息。文件不含 target
  并不等于预测严格样本外。
- 直接拼接训练 run 的 predictions 只能覆盖其评价 split，且依赖 label 样本选择，无法提供
  普通策略需要的完整多年可评分日期。

### 44.2 最终设计与验证

先从单日 runner 中提取唯一 E3 inference runtime 和 scorer：它统一负责 release/config/
checkpoint 校验、模型构建、按需特征窗口、dataset 和 `predict_e1`，模型在同一进程中惰性
加载一次。每日 runner 只保留“选择 D 的完整候选横截面和 production 发布”职责；历史 runner
只保留“选择回放范围、分片、续跑和 backtest 发布”职责；二者继续复用同一个
`build_factor_frame` 与原子 FactorBatch publisher。

历史配置必须显式确认 `acknowledge_non_oos=true`，固定 release、target-free inference
snapshot、日期和可选精确 security IDs。执行按自然年分片，在 CPU 只加载该年实际窗口所需的
features，推理 `batch_size` 继续限制物理批次。每年 FactorBatch 完成后才原子更新 state；恢复
时先重新验证已有 child 的 release/checkpoint/snapshot、日期、样本键、语义身份和文件哈希。
所有年份完成后才生成父 manifest，`verify` 还会拒绝额外文件、缺分片、目录逃逸或 plan/config
漂移。

没有为 HeyBoss 增加第三种 FactorBatch 格式。历史 child 复用
`evaluation_predictions/eligible_scored_cross_section`，这里把枚举解释为 backtest-only 消费
隔离，而不是声称分数来自 predictions 文件；父 manifest 额外永久记录
`strict_out_of_sample=false`、未来参数/scaler/来源修订风险和 `paper_allowed=false`。父目录只在
FacDigger 内部使用，跨项目交付仍是标准两文件 child。

回归验证覆盖非 OOS 确认、配置范围、年度确定性分片、E3 训练→ModelRelease→完整 inference
snapshot→单日 FactorBatch→全历史 FactorBatch 的端到端链路、单日与历史同日 score 一致、
重复运行幂等，以及恶意父分片路径被拒绝。没有在真实全量 EODHD 数据或生产 GPU 上执行本次
回放，因此当前结论是工程能力完成，不是全历史因子已实际产出。

### 44.3 面试版讲法

> 交易系统需要多年因子时，最直接的方法是循环调用每日 signal，但那会把含未来训练信息的
> 历史分数标成可进 paper 的生产来源。我把模型评分从单日编排中抽出来复用，再设计按年、可
> 恢复的固定 release 回放；历史输出继续用同一 FactorBatch 文件契约，却强制走 HeyBoss 的
> backtest-only 来源门禁。这样既没有维护第二套模型实现，也没有为了功能跑通牺牲时间语义。

## 47. INFER-07 / PROD-04：同一种因子契约，不等于内部模型输入相同

### 47.1 暴露的问题与根因

证据等级：`代码审计和工程验证暴露`，不是已发生的实盘事故。

- Finance Transformer 新实验已能输出研究 predictions，但 release、signal、FactorBatch 和
  HeyBoss 导入器的部分代码仍把模型限定为 E3。外部其实只需要日期、证券、分数和 eligibility，
  把网络名称当作协议使消费者无故依赖训练实现。
- 新模型不是“换一个 checkpoint 文件”即可：它需要 14 个个股通道、6 个市场通道和完整日
  Set Transformer。复用有标签 dataset 并填零 target/split，会掩盖训练与生产的边界；提前
  按 HeyBoss 股票池裁剪，又会改变其他股票的上下文以及被选股票的分数。
- 逐层检查生产路径进一步发现：`session_store.py` bootstrap 和每日更新都只保留最新日
  universe。旧单股模型可在构造窗口时重复当日身份，但金融模型的历史 rank 和市场宽度依赖
  当日真实成员。仅修 inference builder 仍无法跑通 Docker hot store 通路。
- Windows run 记录绝对快照路径；scaler 若经 `read_text/write_text` 复制，CRLF 会被转成 LF，
  同值 JSON 也会违反冻结字节哈希。这属于搬迁和不可变产物问题，不应通过改写原 manifest 处理。

### 47.2 最小可用设计

1. 外部仍为五列 FactorBatch。`model_type` 只是规范字符串元数据；双方继续校验排序方向、
   horizon、可用时间、身份、完整覆盖和全部哈希。未知模型不能静默落入 E3 backend。
2. 内部仅设当前确有调用方的两个 backend：PatchTST E1—E3 与 Finance Transformer。统一
   runtime 缓存严格加载的模型，研究回放、每日和历史入口不再各自实现预测。金融模型共享
   `models/finance_scoring.py` 的 forward；目标、split、loss 和评价留在训练/研究层。
3. 原始特征构建与冻结 transform 统一到 `features/pipeline.py`。Finance 使用真正的无标签
   dataset；仅输出 primary horizon。release 绑定市场通道、horizons 和 checkpoint 配置，
   scratch/pretrained 的最终完整权重都不依赖原初始化 encoder 文件。
4. 区分计算与交付：先加载 snapshot 中该日全部 eligible 窗口、分块编码个股、一次运行完整日
   网络，最后筛选交付证券。物理 batch size 不再意味着横截面规模。
5. 热存储保留同窗口逐日 universe；更新时以足够 ADV20 预热重建修订/缺口日期，区间外成员
   不变。上市天数按每只证券的最近历史状态延续。旧的单日 universe 存储明确要求在新目录
   re-bootstrap，不增加假历史兼容层，也不改训练 snapshot。
6. `release create --dataset` 仅覆盖路径定位，仍校验原身份/哈希；scaler 按字节复制。
   Finance 才增加必需的市场输入字段，旧 E3 release 不注入空字段，因此不改变旧内容身份。

### 47.3 验证证据与诚实边界

- 小型 CPU 集成测试完成 scratch 与 pretrained 初始化两条监督路径的训练、原预测严格回放、
  release、无标签每日、历史子集导出和幂等检查；移走训练 run、训练 snapshot 及初始化 encoder
  后仍可推理。整日评分与子集导出精确一致，不同 physical batch 的数值在浮点容差内一致。
- 动态退出/进入股票池的 fixture 验证每日和全历史窗口的 rank/market 特征一致；另将真实
  bootstrap 函数产生的临时 hot store 直接送入 Finance snapshot 与 signal，覆盖此前遗漏的存储边界。
- 热存储测试覆盖历史保留、15 日缺口补齐、与全历史重建的 ADV20/上市天数/eligibility 一致、
  调整因子回填、旧布局拒绝，以及预热不足时 CURRENT 不得推进。
- 跨仓文件验证直接把 FacDigger 集成测试生成的 8 个 E3/Finance FactorBatch（536 行）送入
  HeyBoss 导入器和临时 NT Catalog，覆盖每日、原评价和年度历史分片；逐值核对 score、
  eligibility、release 身份并验证重复导入不新增行。没有手工改写这些交付文件。
- 本轮完整 pytest：FacDigger 209 passed（覆盖率约 77%），HeyBoss 902 passed（覆盖率
  91.64%）。两仓 Ruff 通过，HeyBoss strict mypy 170 个文件通过；FacDigger 锁文件离线检查通过。
- 这不是实盘或真实因子收益验收：未调用 live EODHD、未启动 Docker 调度/IBKR、未写真实
  Catalog，未执行 RTX 训练或 CUDA 推理。在本节记录的阶段，`artifacts826new` 的 dirty Git 谱系
  与 fallback 身份仍由原门禁拒绝，未据此生产真实 release。后续按用户确认调整这些边界，见 §48。

### 47.4 面试版讲法

> 我把“因子语义”与“模型结构”分开：交易系统只消费相同五列，训练侧用两个实际 backend
> 处理不同输入。更关键的是，Set Transformer 的分数取决于完整横截面，所以只导出十只股票
> 也必须先计算整日；而历史 rank 要依赖历史股票池，不能从今日状态倒推。我沿每日数据链路
> 检查到热存储只保留当日成员，连同缺口补齐、冻结 scaler 字节及上市天数一起修复，最后用
> 生产者真正生成的文件跑消费者测试，而不是双方分别写一份自洽 fixture。

## 48. INFER-08 / PORT-01：交付身份、资产位置与联调来源状态不应绑在一起

### 48.1 根因与实际证据

证据等级：`代码审计、已有 Windows 产物与回归测试暴露`，不是实盘事故。

- release 创建扫描整个训练 features 的 fallback ID，推理快照又验证整表 ISIN-only；旧价量
  每日分支甚至在特征构建前排除了非 ISIN 股票。HeyBoss 只交付少量股票时，其他训练股票
  缺 ISIN 也阻止发布。对 Set Transformer，提前删掉这些股票还会改变被交付股票的上下文。
- 仅把“已成功映射的股票”作为交付集合，也是不正确的修复：过期或缺失映射会缩小分母，
  最终报告仍为 100% 覆盖。目标成员和映射有效期必须独立。
- Windows run 的 dataset_path 是 `D:\\...`。已有 `--dataset` 只能解决 release 的一处定位；
  历史导出还比较绝对 output_root、重用原输入路径，因而移动目录后不能验证/续跑。
- Finance Transformer 恢复完整断点前仍先加载预训练 encoder。训练权重、优化器、调度器
  和 RNG 已在断点内，原初始化文件不再需要，却成为迁移后的隐藏依赖。
- dirty 拒绝同时存在于发布端、训练来源、`git_clean: Literal[True]` 和 release loader。
  只删除一个 if 不能真正支持联调；把状态强行写成 true 则会伪造来源。

### 48.2 最终设计与实现

1. `inference/delivery.py` 用两个集合定义交付：`targets` 决定应交付标的/active 日期，
   `identities` 独立给出源 ID、交付 ID、标的 ID、闭区间有效期及 evidence。身份缺失、
   过期、重叠、源行缺失或同日碰撞均失败，不按 ticker 猜测，不静默减少分母。
2. 模型仍处理 snapshot/index 中完整日的 eligible 计算集合，再投影交付子集，不重新排名。
   不交付股票缺 ISIN 不阻止 release；缺少 ISIN 的交付股票可凭已确认映射补足。禁止把
   历史 ISIN 标成另一个 ISIN；双方约定非 ISIN 稳定交付 ID 时，可按可靠区间映射并保留源身份。
3. 三个入口共用交付模块和五列 publisher。每日保留 ineligible/null；历史先从完整候选表
   验证身份，再按 eligible-only 协议输出并审计不合格数。已有 predictions 缺少完整候选表，
   显式目标缺行直接拒绝，不猜测成 ineligible。映射审计位于两文件目录之外，历史配置/plan
   内嵌审计，外部 FactorBatch schema 不变。
4. 生产计算池最低数量移入 `inference.minimum_*`；交付池按显式 profile 精确检查。
   删除全局 ISIN 限制时保留来源证明要求：训练 snapshot 声明过 source manifest，推理就必须
   提供来源证明；通用 adapter 继续验证 accepted 状态及表哈希，不通过身份元数据决定数据质量。
5. `data/paths.py` 统一包内安全相对路径，读取旧反斜杠，拒绝盘符、UNC、上级目录及外部链接。
   release/predict 显式替换本机 snapshot 位置，历史 plan/run/verify 接受本机位置覆盖；
   原 run/config/manifest 不改写，内容 ID、hash、计划和分片校验保留。完整 Finance resume
   直接恢复断点及其中的初始化审计，不读取旧 encoder。
6. `--allow-dirty` 只放行已知 dirty Git 状态，默认仍严格。source.git_clean 如实记录，loader
   验证真实状态一致；未知 Git 状态、非明确 complete 的来源、篡改和旧协议继续拒绝。
   已有干净 release 与旧 ISIN 元信息仍可验证，不增加格式版本或新哈希注册机制。

### 48.3 验证与限制

- 完整 pytest：246 passed，覆盖率约 79%；Ruff、离线锁文件校验与 diff 检查通过。
- 混合身份的真实小型 Finance 模型测试：未知 fallback 留在计算池，交付单股票与完整评分
  后筛选逐值一致；每日、历史和生产 tick 均通过。生产模拟输入 6 个候选/5 个可评分证券，
  交付 1 个已确认目标，证明计算池最低数量不会误用于交付池。
- 迁移测试移走 release、snapshot 和历史输出，使用新位置完成验证、幂等续跑及缺父 manifest
  恢复；原 resolved config 字节不变，改变交付范围仍拒绝。连续两 epoch 与移走 encoder/
  移动断点后的两 epoch 恢复，模型权重精确一致，scheduler/global step/sampler 也一致。
- dirty 发布覆盖发布端、训练端及两者同时 dirty；CLI 可同时指定本机 dataset 和 allow-dirty。
  伪造 git_clean、缺状态、修改 checkpoint 均仍失败。
- HeyBoss 使用本轮 CPU 测试实际产出的 11 个目录、10 个不同 FactorBatch（538 行）完成
  临时 NT Catalog 导入；覆盖 E3、Finance scratch/pretrained、每日/历史及投影后的单标的批次。
  分数、eligibility、release 身份一致，重复导入不新增。未重新序列化或手工补改交付文件。
- 当前验证不包含原生 Windows/CUDA、live EODHD、Docker 长期调度、真实 Catalog 或交易执行。
  未生产 `artifacts826new` 的真实 release。真实联调仍需确认目标清单与映射依据；若直接交付
  跨期 ISIN，HeyBoss 还需日期身份解析，或双方明确约定非 ISIN 的稳定交付 ID。

### 48.4 面试版讲法

> 我没有把发布门禁简单关掉，而是先判断每条检查属于哪一层：Transformer 的计算集合不能
> 缩小，跨系统身份只约束实际交付，但交付分母必须提前确定，不能被映射失败改变。机器路径
> 只是定位，不是内容身份；dirty 是需要诚实记录的来源状态，不等于权重文件损坏。最后用
> 搬迁后的断点连续训练对照、单标的生产 tick 和真实生产者文件的消费者导入，证明这些边界
> 分开后既能跑通，也没有用降低覆盖率或伪造元数据来掩盖问题。

## 49. PROD-05 / INFER-09：局部缺数容忍不是降低完整性，也不是默许空仓

本节记录 2026-09-10 FacDigger 单侧修复的证据和当时限制，保留原貌供追溯。2026-09-16
HeyBoss 保护代码与 826 原 validation 预测的离线历史验收已完成，见[现行交接](../HeyBoss因子联调交接.md)。
这不包含真实每日采集/推理/接纳及持续 paper 验收，不应把本节“当时未完成”继续视为待编码任务。

### 49.1 根因与证据

证据等级：`代码审计与回归测试暴露`，不是实盘误成交事故。

- 每日 runner 以 source 的 `resolved_end == D` 跳过采集。source 提交成功后，推理窗口或
  交付失败会进入等待；下一次仍使用同一份不完整数据，30 分钟“重试”没有实际修复机会。
- 原有最低行数是绝对数量，不足以识别几千只股票突然只剩数百只；如果基于下载后成功行
  计算应交付/应评分集合，缺失还会缩小分母。小交付池和完整计算池也不能共用一个 100 行门槛。
- 通用 source eligibility 可能乐观地保持 true。特征支持历史 mask 不意味着“今日没有任何
  OHLC，也可以给它今天的分数”；只看窗口长度无法保证有真实 D bar。
- Finance Transformer 有共享市场输入，足够多的个股窗口不意味着市场通道/贡献成员完整。
- HeyBoss 审计发现不足 Top N 返回空权重，Actor 仍发送信号，Gateway 对未列入目标的已有
  仓位默认权重为 0。只在排序层过滤缺分股票不能保护仓位。此项本轮未修改 HeyBoss，不能
  声称交易侧已修复。

### 49.2 FacDigger 的修复和设计取舍

1. **来源有效、数据可用、交付完整分开。** `session_store` 保留 schema、日历、身份和复权
   完整性检查；模型/交付最低数量移到 `production/quality.py`。缺单只 D bar 保留真实缺失；
   整市场缺失为可重试的未就绪。非法 OHLC 仍拒绝，并按 symbol 记录数量，不插值或补前值。
2. **先确定分母，再请求数据。** 采集前保存 D 之前已知成熟成员及历史市场计数。同 D 基准
   不可变，SQLite 增补字段但保留原 release/已发布记录。上一日缺失、异常或源提交后进程
   中断未完成评分可用性检查时，不能把残缺 CURRENT 当成下一日的小基准。
3. **计算和交付独立判断。** 保留计算池绝对下限，默认计算损失不超过 5%；交付不可评分
   不超过 20% 且至少 3 只可评分。新成员不能抵消参考成员的缺数据，Finance 另检市场日期、
   mask 和贡献覆盖。以上是初始运行阈值，不是经真实收益证明的最优参数。
4. **缺数据不能伪装成模型输出。** inference index 与真实当日 bars 取交集，缓存快照加载也
   校验当日观测；没有 D bar 的股票 false/null。历史小洞沿用既有 mask；模型 NaN、遗漏应有
   输出或身份问题仍阻断，不能捕获后改成 false。精确日期零可评分允许生成诊断 snapshot，
   生产质量门禁阻止其发布。
5. **先完整计算后交付。** 不复制 scorer，不为每日另写模型通路；完整可评分横截面推理后
   投影已声明交付目标。五列/两文件契约不变，10 只中 1 只不可评分仍交 10 行，
   `missing_eligible_rows=0, ratio=1.0`，因为所有应该得到模型输出的行均有真实分数。
6. **真的重试，且失败日不拖死服务。** 每次未发布尝试重新获取修订，复用公司行动定向回填；
   到截止跳过 D，契约错误阻断 D，服务继续。质量报告与心跳分离；状态变化日志持久去重，
   恢复时记录新状态，不把健康容器当成今日可调仓。
7. **重试需要有界磁盘。** 反复 fresh 修订会生成不同 source/snapshot。常驻服务在等待路径
   也保留 CURRENT/上一 source、最近 10 个日期和每日期最近 2 个完成推理快照；不清理
   FactorBatch、不改训练 snapshot。没有增加哈希分块、格式版本注册或通用插件机制。

### 49.3 验证与边界

- fake EODHD 验证单只非法 OHLC 被拒绝，其他真实格式行继续进入来源，并记录拒绝数量；
  source 单只缺 D bar 不造价，整日缺失不推进 CURRENT。
- runner 验证小范围缺数正常发布、固定覆盖分母、CURRENT 到 D 后重新采集恢复、下一日不
  继承残缺分母，以及源提交后进程中断的恢复边界。模型 NaN 仍 blocked，异常缺数到截止

- 真实小型 CPU Finance 模型验证：缺单只 D bar 的股票保持 null，其余四只完整横截面

### 49.4 面试版讲法

> 我先区分了“数据不够”和“结果不完整”：缺数据可以明确告诉下游这只股票今天不可评分，
> 但声明可评分后就必须有真实模型输出。分母在请求前固定，防止下载失败把覆盖率变成自证；
> 源提交和因子发布也分开，修复了重试一直读旧缺数源的问题。Transformer 还依赖完整横截面
> 和市场输入，所以我没有把交付十只股票等同于只计算十只。最后检查到交易端会把空权重当作
> 清仓，要求它在执行层保护实际数量并扣除占用预算；这项交给交易仓库验收，不能只凭因子
> 文件通过就宣称交易通路安全。

## 52. PROD-08 / FD-04：原子文件发布不等于账本事务幂等

## 54. OPS-02：休眠时间、进程心跳和数据失败不是同一个问题

本次容器 healthy 只证明心跳，不证明交付新鲜。主机曾合盖休眠，但维护唤醒可能允许部分
Docker 工作，不能把合盖至最终唤醒全部算成停机，更不能用休眠解释 MGN 的可复现质量异常。

另一个独立缺陷是在 `_heartbeat_wait` 中累计 `remaining -= waited`：计划等 1,800 秒，
第一次轮询跨过 3,600 秒休眠后，仍继续执行剩余 29 次等待。假时钟复现总墙钟 5,400 秒，
说明唤醒后会继续等过期计划。改为每次比较绝对 UTC 到期时刻，跨首次执行、重试或截止
均重新决策；没有延长截止或自动改变主机电源设置。测试没有实际 sleep。

旧告警按错误类型去重，日志又没有错误正文；最终 expired 覆盖最后根因，让逐次归因变得
不可证明。现在告警仍去重，但每次 attempt 独立记录开始、结束、阶段和耗时；running 保留
前次失败，expired 保留原截止及最后失败，成功才清除。源质量日志与 manifest 保存具体
隔离证据；供应商错误正文在进入持久状态和日志前脱敏，不输出 token。

取舍是没有再造事件数据库：逐次运行证据在容器日志，当前状态和最后根因在 SQLite。
运维仍需保留日志并保证发布窗口主机可用；代码无法在关机的电脑上运行，也不能恢复已经
丢失的历史错误事实。

## 55. OPS-03：异常恢复本身也有内存生命周期

09-23 部署前，用新镜像在断网、生产目录只读挂载条件下重放完整真实缓存，隔离容器在

旧编排在 `except AdjustmentBackfillRequired` 内继续下载、再次读取全历史。异常 traceback

旧实现即使 GC 后仍保留该局部对象，再把编排改为只提取轻量 symbol/date、退出 except 后

退出后内存确实下降，但 source 合并、质量检查和候选回填继续同时持有已经无用的旧表，

输出与 universe 构建错开；别名标量门禁仍检查全部原始行，但只为冲突键生成详细 alias
列表，不给数百万正常键各建列表。对应两个列表范围回归修复前失败，修复后通过。

这说明“单元测试通过”和“异常对象已释放”都不能替代生产规模的容量验收。内存不足在
隔离演练中被发现，失败日志和镜像保留，只有完整源合并和真实模型评分通过后才部署。

验收不仅检查小样本测试，还在相同 Docker VM、同一完整历史和 826 权重上重新测量；内存

Ruff、离线锁文件及 diff 检查通过。

## 57. OPS-04：恢复服务不等于重置失败状态，恢复动作也需要原子性

本次身份错误进入 blocked，Docker 仍 healthy，后续调度只返回同一个阻断结果。修好代码
或重启容器不会自动解除该日的阻断。直接改 SQLite 为 running、删掉失败行或更换 D，会
丢失原覆盖率分母/错误证据，甚至绕开 FD-04 的唯一交付恢复，因此没有采用。

新增显式 `production resume`：使用与常驻服务相同的锁，绑定已检查的 D、release 和
updated_at。先复用 FD-04 对账，有唯一合法原交付只认领；没有交付且仍在原窗口内，检查
源和模型完整性后才排队，由常驻服务执行下一次 fresh 尝试。API、推理和新交付不在维护
命令中运行。已过期日期不复活；损坏和多份交付不靠 resume 洗掉。

新增小型恢复事件表的必要性是：旧账本只保留最新状态，单独写日志再修改状态在退出窗口
中可能只完成一半。恢复原因与原错误/次数在同一个 SQLite 事务内落盘，再更新调度状态；
用原 updated_at 作为比较条件和幂等键，不增加额外哈希、版本或通用工作流框架。

回归覆盖强制退出后的重启/重复请求、审计插入失败事务回滚、并发锁、状态已变化、固定
release、损坏输入、预检跨截止，以及真实小模型产物的截止后原交付认领和歧义拒绝。
普通 pytest 只使用临时数据和 fake transport。恢复接口不是忽略错误的开关；再次失败仍
按正常 runner 分类处理，原错误保留在恢复事件中。正式部署及真实批次另记运行交接。

部署前完整回归 **383 项通过，全仓覆盖率 81%**；在候选镜像中使用真实 826 原交付和隔离
账本，原 runner 与维护恢复入口均通过 FD-04 复验。该验证阶段没有解锁或改写正式账本；
当时部署与恢复尚待确认，不将“代码修好了”与“生产已经恢复”混为一谈。

后续用户确认部署，09-24 11:40 UTC 先备份并停止唯一旧生产者，再由维护入口写入唯一
恢复事件。重复恢复不新增事件、不改变原次数；新常驻生产者 fresh 采集后以 attempts=2
于 11:43:29 UTC 发布 D=09-23，耗时 178.43 秒，早于原截止 1 小时 46 分钟。正式十目标
全部有效，完整计算参考保留，三只身份仍隔离且质量为 degraded；常驻重复调度未重复请求

[正式部署与验收](../826每日生产运行交接.md)。
